자가 개선
루프 엔지니어링은 AI 에이전트를 "한 번의 프롬프트 → 응답"이 아니라 반복 사이클(loop) 단위로 설계하는 방법론이다. LangChain이 제시한 4단계 루프 스택은 아래로 갈수록 자동화 범위가 넓어진다: 작업을 자동화하고(1) → 품질 검증을 자동화하고(2) → 호출 자체를 자동화하고(3) → 마지막엔 개선까지 자동화한다(4). 각 레벨은 이전 레벨을 감싸는 바깥 루프다.

전체 구조 — 루프가 루프를 감싼다

4개의 루프는 병렬 옵션이 아니라 중첩 구조다. 안쪽 루프가 안정된 뒤에 바깥 루프를 추가하는 것이 정석 순서이며, LangChain은 사내 문서화 에이전트(Docs Agent) 하나를 4단계 전부에 걸쳐 예시로 사용한다.

loop-stack
[4] Hill Climbing Loop   : 실행 트레이스 분석 -> 하네스(프롬프트/도구/grader) 자동 수정
 └─ [3] Event-Driven Loop : 외부 이벤트(Slack, cron, webhook)가 실행을 트리거
     └─ [2] Verification Loop : grader가 결과 채점 -> 미달이면 피드백 주고 재시도
         └─ [1] Agent Loop : LLM이 도구를 반복 호출하며 작업 수행

Level 1: Agent Loop — 작업 자동화

가장 안쪽의 기초 루프. LLM이 컨텍스트를 받아 도구를 선택해 호출하고, 결과를 관찰한 뒤 다음 행동을 결정하는 사이클을 작업이 끝날 때까지 반복한다. 수동적인 질문-답변 모델을 능동적인 작업 수행자로 바꾸는 계층이며, Claude Code·Codex 같은 코딩 에이전트의 코어가 바로 이 루프다.

agent-loop 의사코드
# 의사코드
while not task_complete:
    action = llm.decide(context, tools)      # 어떤 도구를 쓸지 결정
    result = execute(action)                 # 도구 실행 (파일 읽기, PR 생성 등)
    context = update(context, result)        # 결과를 관찰하고 컨텍스트 갱신
항목내용
필요 컴포넌트모델, 도구 정의, 태스크 컨텍스트, 반복 제어기(loop controller)
Docs Agent 예시문서 개선 요청을 받으면 저장소 클론 → 파일 읽기 → 문서 수정 → PR 생성까지 도구로 수행
대표 실패 모드무한 루프·과도한 반복, 존재하지 않는 도구 호출 환각, 태스크 오해, 부실한 도구 설명으로 인한 오용
도입 시점항상 출발점. 여러 단계·도구 호출·조건 분기가 필요한 작업이면 이 루프부터
참고 — 이 레벨의 품질은 대부분 도구 설명(description)의 품질이 결정한다. 입력·출력·용도를 명확히 쓴 도구 정의가 프롬프트 튜닝보다 효과가 크다.

Level 2: Verification Loop — 품질 보증

Agent Loop을 채점기(grader)로 감싼다. 에이전트가 작업을 마치면 grader가 결과물을 루브릭(성공 기준)과 대조하고, 기준 미달이면 무엇이 왜 틀렸는지 피드백을 붙여 에이전트에게 재작업을 시킨다. "한 번에 잘하길 기도"하는 대신 "될 때까지 검증-재시도"로 바꾸는 계층이다.

grader는 두 종류를 조합한다.

  • 결정적(deterministic) 검사 — 린터, 테스트, 링크 검증, 스키마 검증. 밀리초 단위로 싸고 빠르다.
  • LLM-as-judge — 톤·범위·의미적 정합성처럼 규칙으로 못 잡는 부분을 채점. 느리고 비싸다.
항목내용
필요 컴포넌트grader(결정적 또는 LLM 판정), 루브릭, 실패 피드백 전달 메커니즘, 재시도 로직
Docs Agent 예시매 시도 후 자동으로 하이퍼링크 유효성·CI 통과·요청 범위 일치를 검사 → 이 오류 유형은 사람 리뷰 불필요
대표 실패 모드과도하게 엄격한 grader의 불필요한 재시도, 모호한 루브릭의 일관성 없는 채점, 품질 향상 없는 지연·비용 증가
도입 시점프로토타입 → 프로덕션 전환 시 즉시. 오류가 실제 비용을 만드는 환경이면 필수
주의 — 비용 최적화의 핵심은 순서다. 싼 결정적 검사를 먼저 돌리고, 통과한 것만 LLM grader로 보낸다. 반대로 하면 grader가 병목이자 비용 폭탄이 된다.

Level 3: Event-Driven Loop — 인프라화

앞의 두 루프는 여전히 사람이 "실행해"라고 눌러야 돈다. Level 3은 호출 자체를 자동화한다. Slack 메시지, cron 스케줄, webhook 같은 외부 이벤트가 에이전트를 트리거하면서, 에이전트는 일회성 도구에서 조직 인프라에 상주하는 구성 요소로 바뀐다. LangChain은 이 전환을 "장난감(toy)에서 진짜 인프라(real infrastructure)로"라고 표현한다.

항목내용
필요 컴포넌트이벤트 소스(스케줄·webhook·채널 메시지), 트리거 설정, 시스템 연동 계층, 결과를 다운스트림에 반영하는 응답 메커니즘
Docs Agent 예시사내 Slack의 #docs-plz 채널에 메시지가 올라오면 자동 실행 — 수동 호출이 사라짐
대표 실패 모드이벤트 폭주로 인한 리소스 고갈, 연결 장애로 인한 이벤트 유실, 연쇄 장애, 트리거 기반 이슈의 디버깅 난이도
도입 시점Level 1~2가 안정적으로 검증된 후. 조직 단위로 자동화를 확장할 때 필수
참고 — 상시 대기형 어시스턴트에는 주기적으로 스스로 깨어나 상태를 점검하는 "heartbeat" 패턴이 함께 쓰인다. Cowork·Claude Code의 예약 작업(scheduled task)이 이 레벨의 구현체다.

Level 4: Hill Climbing Loop — 자가 개선

가장 바깥의 루프이자 가장 성숙한 단계. 프로덕션에서 쌓인 실행 트레이스(trace)를 분석 에이전트가 검토해 성공·실패 패턴을 찾고, 하네스 구성 — 프롬프트, 도구 선택, grader 로직 — 을 자동으로 수정한다. 핵심은 화살표의 방향이다: 이 루프의 귀환 화살표는 단순히 처음으로 돌아가는 게 아니라 안쪽 Agent Loop의 설정을 직접 고쳐 넣는다. 실행할수록 시스템이 좋아지는 복리 구조가 여기서 생긴다.

항목내용
필요 컴포넌트전체 실행 트레이스 수집, 분석 에이전트, 구성(config) 관리, 업데이트 배포 메커니즘, 성공/실패 피드백 신호
Docs Agent 예시트레이스 분석으로 반복되는 실패 패턴 감지 → 동일 문제가 여러 트레이스에서 확인되면 해당 프롬프트·도구 수정 이슈를 자동 등록
대표 실패 모드트레이스 오독으로 인한 잘못된 결론, 나쁜 자동 업데이트로 인한 성능 저하, 폭주 최적화 사이클, 피드백 신호 부족, 버전 간 설정 드리프트
도입 시점Level 1~3 안정화 + 충분한 프로덕션 데이터 축적 이후. 최후순위로 추가
참고 — open-weight 모델을 쓰는 경우 트레이스를 하네스 개선을 넘어 RL 파인튜닝 데이터로 되먹여 모델 자체를 개선하는 확장도 가능하다.

하네스 엔지니어링과의 관계

하네스 엔지니어링은 "Agent = Model + Harness"라는 등식에서 모델을 뺀 전부 — 도구, 제약, 스캐폴딩, 피드백 장치 — 를 설계하는 실천이다. Thoughtworks의 Birgitta Böckeler는 이를 행동 전 방향을 잡는 Guides(컨벤션·문서·지침)와 행동 후 자기수정을 유발하는 Sensors(린터·테스트·리뷰 에이전트)로 정리했다.

구분하네스 엔지니어링루프 엔지니어링
초점에이전트를 둘러싼 정적 환경·구조그 환경이 반복 실행되는 사이클 자체
질문어떤 도구·제약·피드백 장치를 줄 것인가언제 실행되고 어떻게 검증·재시도·개선되는가
단위실행 환경(tools, guardrails, sensors)반복 사이클(trigger → 실행 → 검증 → 재실행)
관계하네스는 루프가 최적화하는 대상이고, 루프 엔지니어링은 그 하네스를 피드백으로 굴리고 개선하는 방법론이다

계보로 보면 프롬프트 엔지니어링(2022~24, 표현 최적화) → 컨텍스트 엔지니어링(2025, 모델에 보이는 정보 큐레이션) → 하네스 엔지니어링(2026, 실행 환경 전체 설계) → 루프 엔지니어링(2026, 전부를 돌게 만드는 반복 계층)으로 누적되어 왔다. 대체가 아니라 레이어 추가다.

사람은 어디에 개입하는가

네 루프 모두 자연스러운 체크포인트에 human-in-the-loop을 끼워 넣을 수 있고, LangChain은 이를 모든 프레임워크의 1급 기본 요소(first-class primitive)로 다룬다.

루프사람의 개입 지점
Agent Loop민감한 도구 실행(배포·삭제 등) 전 승인
Verification Loop주관적 품질 판단이 필요한 항목의 수동 채점
Event-Driven Loop결과물이 최종 사용자에게 도달하기 전 검토
Hill Climbing Loop자동 생성된 설정 변경의 배포 전 검증

정리

Level루프자동화 대상핵심 컴포넌트도입 시점
1Agent Loop작업 수행모델 + 도구 + 반복 제어항상 출발점
2Verification Loop품질 검증grader + 루브릭 + 재시도프로덕션 전환 시 즉시
3Event-Driven Loop호출·트리거이벤트 소스 + 트리거 설정Level 1~2 안정화 후
4Hill Climbing Loop시스템 개선트레이스 수집 + 분석 에이전트충분한 운영 데이터 축적 후

한 줄로 요약하면: Level 1은 일을 자동화하고, Level 2는 검증을 자동화하고, Level 3은 호출을 자동화하고, Level 4는 개선을 자동화한다. 각 단계에서 사람의 판단은 제거되는 게 아니라 더 높은 레버리지 지점 — 하네스와 루프 설계 자체 — 으로 이동한다.
