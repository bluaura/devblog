Phone Harness는 AI 에이전트가 실제 iPhone·Android를 탭, 입력, 스크롤로 조작하게 해주는 오픈소스 도구다. 소스를 읽어 보니 미러링을 직접 구현한 것이 아니라 Apple의 iPhone 미러링 앱 창을 밖에서 캡처하고 OCR로 읽은 뒤 이벤트를 주입하는 구조였다. 그래서 내 iPhone을 직접 조작하는 기능은 macOS에서만 되고, Windows에서는 Android(adb)와 유료 클라우드 iPhone만 쓸 수 있다.

Phone Harness란

Claude Code, Codex 같은 에이전트가 사람처럼 폰 화면을 보고 누르게 해주는 도구다. 탈옥도, Xcode도, 폰에 설치하는 앱도 필요 없다는 점을 내세운다. 오픈소스 하네스는 무료이고, 그 위에 클라우드 폰 임대 사업을 얹은 구조다.

항목내용
만든 곳Phone Harness Inc., Y Combinator Fall 2026 배치
창업자Shawn Pana (1인 창업, 이전에 Browser Use 그로스 담당)
공개 시점오픈소스는 2026년 8월경부터 알려졌고, 11월 4일 클라우드 폰과 함께 정식 런칭
언어Python 3.10 이상
연동에이전트 스킬(SKILL.md) + CLI, Hermes 플러그인, OpenClaw 플러그인, MCP 서버(클라우드 폰 전용)

에이전트는 CLI의 표준 입력으로 짧은 Python 스크립트를 넘긴다. 헬퍼 함수가 미리 import되어 있다.

terminal (README 예제)
phone-harness <<'PY'
open_app("Notes")
tap_text("New Note")
type_text("hello from the harness")
print([o["text"] for o in screen()][:10])
PY

iPhone 미러링은 어떻게 구현했나

핵심은 미러링을 구현하지 않았다는 것이다. 화면 전송과 터치 전달은 macOS 15에 들어간 Apple의 iPhone 미러링 앱(com.apple.ScreenContinuity)이 전부 한다. Phone Harness는 그 창에 눈과 손을 붙일 뿐이다.

단계구현
창 찾기번들 ID로 PID를 얻고 CGWindowListCopyWindowInfo에서 해당 PID의 창을 고른다. 창 이름은 언어별로 달라서 쓰지 않는다
캡처기본은 CGWindowListCreateImage로 창 ID를 지정해 캡처한다(다른 창에 가려져도 가능). 실패하면 screencapture -l로 폴백
화면 읽기Apple Vision의 VNRecognizeTextRequest로 OCR을 돌리고, 글자 박스를 전역 화면 좌표로 변환한다
탭·드래그비공개 SkyLight API SLPSPostEventRecordTo로 PID와 창 ID에 마우스 이벤트 레코드를 직접 전달한다. 포커스를 뺏지 않는다
폴백 입력SkyLight 로드에 실패하면 창을 맨 앞으로 올리고 CGEventPost(kCGHIDEventTap)로 주입한다
스크롤커서를 약 0.3초 동안 창 위로 옮겨 휠 이벤트를 보낸 뒤 원위치로 되돌린다
텍스트 입력기본은 Mac 클립보드에 넣고 Cmd+V. 옵션으로 US 배열 HID 키코드 타이핑
홈·앱 실행미러링 앱 단축키를 쓴다. Cmd+1 홈, Cmd+2 앱 전환, Cmd+3 Spotlight에 앱 이름 입력
연결 상태창 안에 접근성 요소가 없으면 라이브 스트림, 있으면 안내 화면으로 판정한다. AXObserver로 변화를 감시

왜 OCR인가

미러링 창 안쪽은 영상 스트림이라 macOS 접근성 API가 아무것도 보지 못한다. 그래서 화면에 보이는 글자를 인식해 좌표를 얻는 방법밖에 없다. 반대로 이 성질을 연결 상태 판정에 그대로 쓴다. "iPhone 사용 중" 같은 안내 화면은 일반 Mac 뷰라서 버튼과 라벨이 접근성 트리에 나타나고, 정상 스트림이면 자식 요소가 0개다. 문구를 검색하지 않으니 언어 설정과 무관하게 동작한다.

포커스를 뺏지 않는 입력

일반 CGEvent는 창이 맨 앞에 있어야 전달된다. 그러면 에이전트가 일하는 동안 사용자 화면을 계속 가로채게 된다. 기본 백엔드는 창 관리자 yabai가 쓰는 것과 같은 방식으로, 0xf8 바이트 이벤트 레코드를 만들어 프로세스에 직접 보낸다. 아래는 저장소의 background.py에서 발췌해 줄인 것이다(MIT 라이선스).

background.py (발췌·축약)
def _post(pid, wid, etype, gx, gy, lx, ly):
    buf = (ctypes.c_uint8 * 0xf8)()
    buf[0x04] = 0xf8                            # 레코드 길이
    buf[0x3a] = 0x10
    struct.pack_into("<I", buf, 0x3c, wid)      # 대상 창 ID
    struct.pack_into("<dd", buf, 0x10, gx, gy)  # 전역 좌표
    struct.pack_into("<dd", buf, 0x20, lx, ly)  # 창 내부 좌표
    buf[0x08] = etype                           # 1=down, 2=up, 6=dragged
    psn = _PSN()
    _appserv.GetProcessForPID(pid, ctypes.byref(psn))
    _sky.SLPSPostEventRecordTo(ctypes.byref(psn), ctypes.byref(buf))

키 입력에서 알아낸 것들

소스 주석에 시행착오가 꽤 자세히 남아 있다. 미러링 창을 자동화하려는 사람에게 쓸모 있는 내용이다.

  • iPhone 미러링은 원시 HID 키코드만 iOS로 넘기고, 이벤트에 실린 유니코드 문자열과 수정키 플래그는 버린다. 그래서 Shift는 플래그가 아니라 실제 키를 누른 상태로 만들어야 한다.
  • 키 입력으로 타이핑하면 iOS 자동 수정이 단어를 바꿔 버린다. 정확한 문자열이 필요하면 붙여넣기 경로가 안전하다.
  • 붙여넣기 후 이전 클립보드를 바로 복원하면, 폰이 클립보드를 늦게 가져가면서 이전 내용(URL, 토큰 등)이 입력될 수 있다. 그래서 기본값은 복원하지 않는다.
  • 스크롤 이벤트는 활성 앱이 아니라 실제 커서 아래의 창으로 전달된다. PID로 직접 보내는 방식은 통하지 않는다.

Android는 미러링이 없다

Android 백엔드는 adb만 쓴다. 화면을 PC로 띄울 필요가 없고 OCR도 기본적으로 필요 없다.

기능명령
캡처adb exec-out screencap -p
화면 텍스트uiautomator dump로 접근성 트리를 읽는다. OS가 준 정확한 값이다
입력input tap, input swipe, input motionevent, input keyevent, input text
연결USB 디버깅 또는 무선 디버깅(Android 11 이상, 페어링 코드)

scrcpy가 설치되어 있으면 창을 띄워 주지만, 이것은 사용자가 지켜보기 위한 뷰어일 뿐 제어 경로가 아니다.

아키텍처

구조
에이전트 (Claude Code, Codex, Hermes, OpenClaw)
   |  SKILL.md를 읽고 Python 스크립트 작성
   v
CLI: phone-harness <<'PY' ... PY
   |  stdin 코드를 exec, 상주 데몬 없음
   v
helpers.py   tap_text, scroll_collect, open_app ...
   + agent_helpers.py (에이전트가 직접 추가하는 헬퍼)
   v
transport.py   Backend.send(op, **kw)   공통 op 26개
   |
   +-- IPhone   ios.py -> background.py / mirror.py + ocr.py
   |            macOS 전용
   +-- Android  android.py -> adb
   |            macOS, Linux, Windows
   +-- Remote   remote.py -> POST <url>/op (Bearer 토큰)
                클라우드 iPhone, OS 무관

설계에서 눈에 띄는 점은 세 가지다.

  • 의미 단위의 공통 op. screen.text, input.tap, nav.home, apps.launch처럼 "무엇을 하는가"로 이름을 붙였다. iPhone에서는 Cmd+1 키 입력이고 Android에서는 KEYCODE_HOME이지만 스크립트는 같다. 헬퍼 계층에는 플랫폼 정보가 전혀 없다.
  • 없는 기능은 흉내 내지 않는다. iPhone에는 시스템 뒤로가기, 앱 목록, UI 트리가 없으므로 Unsupported 예외를 낸다. 가장자리 스와이프로 뒤로가기를 흉내 내면 호출자가 진짜 결과와 구분할 수 없기 때문이라고 주석에 적혀 있다.
  • 출처를 값에 붙인다. 화면 텍스트마다 source 필드가 있어서 OCR 추정값(pixels)과 OS가 준 값(tree)을 구분한다. OCR도 깨끗한 글자에는 신뢰도 1.0을 주기 때문에 신뢰도만으로는 둘을 구별할 수 없다.

데몬이 없다는 점도 특징이다. 창 위치와 캡처를 호출할 때마다 다시 조회하고, 매 실행이 독립적으로 끝난다. 부족한 기능은 에이전트가 agent_helpers.py에 직접 써 넣으면 다음 실행부터 자동으로 불러온다.

Windows에서 쓸 수 있나

Phone Harness 자체는 Windows에서 설치되고 동작한다. 다만 쓸 수 있는 대상이 줄어든다.

대상macOSWindowsLinux방식
내 iPhone (로컬)가능불가불가iPhone 미러링 창 조작
내 Android (로컬)가능가능가능adb, USB 또는 Wi-Fi
클라우드 Android가능가능가능adb 원격 접속
클라우드 iPhone가능가능가능HTTPS로 op 전송

로컬 iPhone이 Windows에서 안 되는 이유는 코드에 그대로 드러난다. 플랫폼 분기에서 macOS가 아니면 바로 에러를 낸다.

transport.py (발췌·축약)
if platform in ("ios", "iphone", "ipad"):
    if sys.platform != "darwin":
        raise RuntimeError(
            "iPhone control needs macOS "
            "(it drives the iPhone Mirroring app)")
    return importlib.import_module(".ios", __package__).IPhone(**kw)
if platform == "android":
    return importlib.import_module(".android", __package__).Android(**kw)

의존성도 마찬가지다. pyproject.toml에서 pyobjc의 Quartz, Vision, Cocoa, ApplicationServices는 sys_platform == 'darwin' 조건이 붙어 있어 macOS에서만 설치된다. 근본 원인은 iPhone 미러링 앱이 Windows에 없다는 것이다.

Windows에서 iPhone을 다루는 유일한 길은 클라우드 iPhone이다. 공식 문서는 이를 "우리가 운영하는 Mac 위의 실제 iPhone"이라고 설명한다. 클라이언트는 op 하나를 POST 한 번으로 보내고 스크린샷은 base64 PNG로 받는다. 서버 코드는 비공개지만, 서버 쪽에서 같은 Mac 방식을 돌리는 것으로 보인다(추정).

주의 — 클라우드 iPhone은 내 폰이 아니라 Phone Harness가 보유한 폰을 빌려 쓰는 것이다. 내 iPhone에 깔린 앱과 로그인 상태를 Windows에서 조작하는 용도로는 쓸 수 없다.

Windows에서 내 iPhone을 직접 조작하려면

Phone Harness 밖에서 같은 구조를 만들 수 있는지 따져 봤다. Windows의 휴대폰과 연결(Phone Link)은 iPhone에서 통화, 메시지, 알림 정도만 지원하고 화면 미러링과 입력 전달은 제공하지 않는 것으로 알고 있다. 그러면 눈과 손을 따로 조합해야 한다.

역할방법제약
눈 (화면)AirPlay 수신 프로그램으로 iPhone 화면을 Windows 창에 띄우고 캡처 + OCR보기 전용이라 입력은 전달되지 않는다
손 (입력)PC가 블루투스 HID 마우스·키보드로 iPhone에 연결절대 좌표를 줄 수 없어 포인터 위치 보정이 필요하다
정석 자동화WebDriverAgent빌드와 서명에 Mac과 Xcode가 필요하다
미검증 — 이 절은 일반 지식에 기반한 검토이며 직접 구현해 확인한 내용이 아니다. Phone Link의 지원 범위도 작성 시점 이후 바뀔 수 있다.

한계와 리스크

저장소가 스스로 밝힌 한계

  • iPhone 잠금을 해제하면 미러링이 멈춘다. PIN으로 잠긴 Android는 사용자가 풀어야 한다.
  • OCR은 글자만 본다. 라벨 없는 아이콘은 스크린샷을 비전 모델에 넘겨야 한다.
  • 멀티터치, 카메라, Face ID 흐름은 지원하지 않는다. DRM 영상은 검게 나온다.

코드를 읽고 본 약점

  • 기본 입력 경로가 비공개 SkyLight API다. macOS 업데이트로 깨질 수 있어서 폴백 경로를 유지하고 있다.
  • 키 입력은 US 배열 키코드만 지원한다. 한글은 붙여넣기 경로로만 들어간다.
  • 붙여넣기 후 입력한 텍스트가 Mac 클립보드에 남는다.

사업·보안 측면 (개인 해석)

  • 핵심 코드가 작고 공개되어 있어 기술 장벽은 낮다. 차별점은 실제 번호, 2단계 인증, 로그인 유지가 되는 클라우드 실기기 인프라 쪽이다.
  • 사이트가 "앱은 사람으로 인식한다"와 폰 팜 구축을 전면에 내세운다. 앱 약관 위반이나 봇 탐지 우회 용도로 쓰일 소지가 있다.
  • 개인 폰을 연결하면 에이전트가 결제, 메시지, 인증 코드에 접근한다. 프롬프트 인젝션이 일어났을 때 피해 범위가 크다.
  • arXiv의 "PhoneHarness" 논문(2606.14832)은 폰 에이전트 벤치마크 연구로, 이 제품과는 별개다.

정리

질문답
미러링을 직접 구현했나아니다. Apple의 iPhone 미러링 앱 창을 캡처, OCR, 이벤트 주입으로 조작한다
macOS에서만 되나로컬 iPhone 제어만 macOS 전용이다(macOS 15+, iOS 18+)
Windows에서 쓸 수 있나Android(adb)와 클라우드 폰은 된다. 내 iPhone은 안 된다
Windows에서 iPhone은유료 클라우드 iPhone이 유일하다. 내 폰이 아닌 임대 폰이다
아키텍처의 핵심공통 op 26개 위에 헬퍼를 얹고, 백엔드 3종(iPhone, Android, Remote)을 갈아 끼운다
배울 점미지원 기능은 예외로 드러내고, 값마다 출처(OCR인지 트리인지)를 붙이는 설계
