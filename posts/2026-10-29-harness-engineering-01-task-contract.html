코딩 전에 '완료의 의미'를 정한다

여기서 '계약'은 법적 문서가 아니라 사람과 에이전트가 공유하는 짧은 작업 명세다. "파일 전송 기능을 개선해 줘"만으로는 속도, 화면, 오류 처리 중 무엇을 고쳐야 하는지 모호하다. 구현을 시작하기 전에 이 선택지를 줄이는 것이 목표다.

모델과 하네스의 역할

모델은 코드와 다음 행동을 판단한다. 하네스는 모델이 문맥과 도구를 받아 작업하고 결과를 확인할 수 있도록 둘러싼 실행 환경과 제어 구조다. 작업 계약은 하네스에 넣을 입력 규칙의 한 부분이며, 계약 문서만으로 실행이나 검증이 강제되지는 않는다.

이번 회차에서 만드는 것

파일 전송률 계산 기능에 대한 한 화면 분량의 작업 명세를 만들고, 에이전트가 그 범위 안에서 작업했는지 확인한다. 별도 에이전트 프레임워크나 자동화 도구는 설치하지 않는다.

왜 여기서 시작하나 — Anthropic은 장시간 코딩 실험에서 에이전트가 기능을 너무 일찍 완료로 판단하는 문제를 관찰했고, 구체적 기능 목록과 테스트로 상태를 확인하는 방식을 사용했다. [1] 이 글의 '작업 계약'은 그 원칙을 작은 앱 개발 업무에 적용한 교육용 양식이며, 특정 업체의 공식 표준 이름은 아니다.

완료 게이트를 이해하기 위한 출발점이기도 하다. 게이트가 판정하려면 먼저 무엇을 완료로 인정할지 정해야 한다.

작업 계약을 더 깊이 이해하기

동료에게 일을 인계한다고 생각하기

동료에게 "진행률 버그를 고쳐 주세요"라고만 말하면, 동료는 어떤 화면과 어떤 입력에서 문제가 생겼는지부터 찾아야 한다. "1바이트를 3바이트로 나누면 33%로 표시하고, 계산 함수만 수정해 주세요"라고 전하면 시작점과 도착점이 선명해진다. 에이전트에게도 같은 정보를 정리해 전달하는 것이 작업 계약이다.

핵심은 지시를 길게 쓰는 것이 아니라 구현 결과가 달라질 수 있는 선택을 미리 정하는 것이다. 출력 형식, 잘못된 입력의 처리, 바꿔도 되는 범위처럼 결과에 영향을 주는 내용을 우선 적는다.

작업 계약의 네 가지 질문

질문항목이번 예시
1. 무엇을 받나?입력전송량과 전체 크기 (예: 1바이트, 3바이트)
2. 어디까지 바꾸나?범위계산 함수와 검증 코드. 화면·통신은 제외
3. 어떻게 동작하나?기대 동작백분율의 소수점 버림 (예: 1 / 3 → 33)
4. 무엇으로 확인하나?증거실제 검사 결과와 변경 내역 (예: 기대값 33, 실제값 33, 통과)
  • 입력은 에이전트가 다룰 재료다. 형식과 단위를 정하면 바이트와 킬로바이트를 혼동하는 일을 줄인다.
  • 범위는 이번 변경의 경계다. 진행률 계산을 고치려다 파일 전송 구조까지 바꾸는 일을 막는다.
  • 기대 동작은 결과가 옳은지 판단할 기준이다. 정상값뿐 아니라 전체 크기가 0인 경우처럼 애매한 입력의 정책도 정한다.
  • 증거는 기준을 실제로 만족했는지 확인할 재료다. 예상값을 적은 표와 실제 실행 결과는 서로 다른 정보다.
한 항목이 빠지면 — "소수점 처리"가 비어 있으면 1 / 3의 결과를 33으로 할지 33.3으로 할지 구현자가 결정해야 한다. "증거"가 비어 있으면 코드가 생겼다는 사실만으로 완료를 판단하기 쉽다.

계약은 실행 중에도 기준으로 쓴다

흐름은 계약 → 구현 → 확인 → 판정이다.

  1. 작업 계약을 정한다.
  2. 에이전트가 구현하고 변경 내역과 검사 결과를 남긴다.
  3. 계약과 실제 결과를 비교한다.
  4. 기준 충족·증거 있음이면 완료로 인정. 불일치·증거 부족이면 수정 또는 보류하고, 수정 가능하면 2단계로 돌아간다.

단계별로 지킬 원칙은 다음과 같다.

  • 시작할 때 — 무엇을 만들지와 무엇을 검사할지를 함께 정한다. 구현 후 마음에 드는 결과에 맞춰 기준을 바꾸지 않는다.
  • 구현한 뒤 — 코드 변경과 실제 검사 결과를 받는다. "아마 맞을 것 같다"는 설명은 실행 근거를 대신하지 못한다.
  • 판정할 때 — 기대 동작과 범위를 만족했는지 확인한다. 실패하면 수정하고, 실행 환경이 없어 확인할 수 없으면 미검증으로 남긴다.

이 흐름은 설계 개념도다. 이번 회차에서는 사람이 결과를 대조하고, 이후 회차에서 이를 도구와 완료 게이트로 연결한다.

작업 계약과 하네스의 연결

CLAUDE.md 같은 프로젝트 지침에는 여러 작업에 반복 적용할 규칙을 두고, 이번 작업의 입력·범위·기대값은 개별 작업 계약에 두는 방식을 생각할 수 있다. 실제로 어떤 파일을 읽는지는 사용하는 도구의 설정에 따라 다르다.

하네스는 이 계약을 에이전트에게 전달하고, 실행 도구를 연결하고, 결과 확인 절차에서 다시 참조할 수 있다. 계약은 판단 기준이고, 그 기준을 실행에 연결하는 장치는 별도로 필요하다. 이번 회차는 기준을 만드는 부분부터 연습한다.

모든 예외와 구현 방법까지 정해야 하나? — 결과를 바꾸는 중요한 선택부터 적는다. 이번 예에서는 소수점 처리와 잘못된 입력의 정책이 해당한다. 내부 변수 이름이나 계산 순서까지 지정할 필요는 없다. 확인할 수 없는 제품 정책이 있다면 에이전트가 임의로 확정하게 두지 말고, 필요한 결정을 표시하게 한다.

예시: 파일 전송률 계산을 맡긴다면

구분요청문제 또는 보완
기준이 모호한 요청"파일 전송 진행률이 이상해. 고쳐 줘."어떤 입력에서 이상한가? 소수점은 반올림하나? 잘못된 입력은 어떻게 처리하나?
범위를 정한 요청"전송 바이트 수와 전체 바이트 수를 받아 정수 백분율을 구하는 함수만 구현해 줘. 소수점은 버리고, 잘못된 입력은 예외로 처리해 줘."여기에 아래의 입력·예상 결과와 증거 제출 조건을 붙인다.

계약 명세

계약 항목이번 실습의 명세
입력C#의 long sent, long total. 단위는 바이트.
기대 동작int GetProgressPercent(long sent, long total). 정상 입력은 0~100의 정수 백분율, 소수점 버림.
오류 처리total <= 0, sent < 0, sent > total이면 ArgumentOutOfRangeException.
변경 범위계산 함수와 이를 확인할 최소 테스트/검사 코드. UI·통신·재시도 로직은 다루지 않음.
완료 증거변경 파일 목록, 아래 사례의 실제 검증 결과, 실행 명령. 실행하지 못했으면 그 이유와 미검증 항목.

실제 프로젝트를 진단한 내용이 아닌 교육용 과제다. 0바이트 파일은 여기서 오류 입력으로 정했으며, 제품에서는 별도 정책을 정할 수 있다.

구현 전에 고정할 기대 결과

입력 (sent, total)기대 결과확인할 것
(0, 100)0전송 시작
(50, 100)50중간 상태
(1, 3)33소수점 버림
(100, 100)100완료 경계
(0, 0)지정한 예외전체 크기 오류
(-1, 100)지정한 예외음수 전송량
(101, 100)지정한 예외전체 크기 초과
(long.MaxValue, long.MaxValue)100큰 값에서 중간 계산 오버플로 방지

이 표는 요구사항과 예상값이다. 실제 테스트를 실행한 결과표가 아니다.

25분 실습

준비물: Claude 또는 Codex, 수정해도 되는 작은 C# 프로젝트. 새 프로젝트를 만든다면 .NET SDK가 설치된 환경을 쓴다. 기존 테스트 도구가 있으면 그대로 사용한다.

  1. 0~5분 · 계약을 적는다. 위의 계약 항목을 작업 메모에 복사한다. 자신의 업무로 바꿔도 좋지만 범위는 함수 하나 정도로 잡는다.
  2. 5~8분 · 빈틈을 점검한다. "이 계약만 보고 구현자가 판단해야 할 내용이 남아 있는가?"를 확인한다. 모호한 부분은 구현 전에 한 줄로 결정한다.
  3. 8~18분 · 에이전트에게 맡긴다. 아래 요청문을 전달해 구현과 최소 검증을 진행한다. 기존 프로젝트의 구조와 지침을 먼저 읽게 한다.
  4. 18~23분 · 결과를 대조한다. 변경 파일과 실제 실행 출력을 확인한다. 기대 결과 표의 각 행에 통과·실패·미실행 중 하나를 기록한다.
  5. 23~25분 · 계약을 한 줄 개선한다. 에이전트가 추측해야 했던 내용이나 예상 밖 변경을 하나 적고, 다음 계약에서 그 부분을 명확히 한다.
기대 산출물 — (1) 작업 계약 1개 (2) 계산 함수와 최소 검증 코드 (3) 사례별 결과와 실행 근거 (4) 계약 개선 메모 1줄.

C# 실행 환경이 없다면 설치 대신 계약 작성과 모호함 점검까지만 수행한다. 코드 생성·출력 검토는 가능하지만 실행 여부는 '미실행'으로 남긴다. 이 실습의 핵심은 작업 계약을 구체적으로 작성하는 것이다.

결과 확인 체크리스트

"완료했습니다"라는 응답과 실제 근거를 대조한다.

  • 입력·출력·오류 동작을 구현 전에 정했다. 예: 1/3을 반올림할지 추측하게 두지 않았다.
  • 변경 파일과 diff를 확인했고, UI·통신 등 범위를 벗어난 수정이 없다.
  • 검증 코드가 기대 결과를 실제로 비교하며, 값이 다르거나 필요한 예외가 없으면 실패한다. 화면에 숫자만 출력하는 것은 부족하다.
  • 정상·경계·잘못된 입력·큰 값의 고정 사례를 모두 확인했다. 실패하거나 생략한 사례가 숨겨져 있지 않다.
  • 실제 명령과 실행 결과가 남아 있다. 실행 환경이 없다면 미실행임을 명확히 표시했다.
  • 실패를 숨기기 위해 기대 결과를 바꾸거나 검증 사례를 삭제하지 않았고, 계약 개선 메모를 한 줄 남겼다.
에이전트가 "8개 모두 통과"라고 했다면 — 각 사례가 실제로 호출되었는지, 예상값과 다르면 검사가 실패하도록 되어 있는지, 결과가 지금의 변경 코드에 대한 것인지 확인한다. 출력 근거가 없으면 '통과'라는 문장만으로 검증했다고 볼 수 없다. 자동으로 완료를 막는 구조는 이후 '완료 게이트' 회차에서 다룬다.
