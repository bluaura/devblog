2. 변경이 작성부터 배포까지 거치는 일곱 단계

① PR 전 검증과 독립 리뷰

작성 에이전트에게 실행할 수 있는 완료 조건을 줍니다. 테스트 명령, 빌드, 실제 앱 동작, 디자인과 비교할 스크린샷 등이 여기에 해당합니다. 에이전트는 실행 결과를 제시합니다. 이어서 구현 대화에 참여하지 않은 새로운 컨텍스트의 서브에이전트가 diff를 읽습니다. 팀원들은 PR 전 버그 탐색, 변경 단순화, E2E 확인용 내부 스킬도 사용하고, UI 변경에는 디자인 기준을 적용합니다. 원문 · 검증에 관한 후속 글

두 검증은 보는 대상이 다릅니다. 작성 에이전트는 작업 중의 결정과 제약을 알아 실패 원인을 빠르게 좁힐 수 있습니다. 독립 리뷰어는 PR의 의도와 실제 diff를 맞대어 빠진 분기나 호출자에 미치는 영향을 봅니다. 예를 들어 전송 화면을 바꿨다면 빌드는 컴파일 가능 여부, 실기기 실행은 사용 중 화면 동작, diff 리뷰는 취소 처리가 어디로 전달되는지를 확인합니다.

② 여러 에이전트가 결함 후보를 탐색하고 별도의 그룹이 검증

첫 번째 그룹은 PR의 목적, diff, 관련 저장소 코드를 보고 결함 후보를 병렬로 찾습니다. 버그 수정 PR이면 수정이 실제 원인까지 해결하는지 살핍니다. 두 번째 그룹은 각 후보를 코드에 대조하고, 내부 흐름에서는 충분한 동의를 받은 후보만 게시합니다. 중복을 제거하고 중요도별로 정렬한 뒤 해당 줄에 코멘트와 요약을 남깁니다. 팀은 스타일, 진단 메시지, 정리 작업에 그치는 지적을 걸러내는 필터를 내부 PR에서 A/B 테스트했습니다. 원문 · Code Review 공식 문서

표시의미

Nit상대적으로 중요도가 낮은 지적
Pre-existing현재 PR이 도입하기 전부터 존재한 문제

후보 검증과 중요도 판단은 서로 다른 질문입니다. 코드상 실제로 일어날 수 있는 동작인지 검증한 뒤, 지금 PR에서 처리할 가치가 얼마나 큰지 판단합니다. 필터가 엄격하면 근거 약한 후보는 줄어들고, 실제 결함도 탈락할 수 있습니다. 그래서 팀은 탐색 직후, 검증 직후, 최종 리뷰의 탐지율을 각각 잽니다. 검증에 관한 후속 글

③ 보안 리뷰와 미해결 지적에 대한 머지 차단

사내에서는 일반 버그 리뷰와 보안 리뷰의 열린 지적이 모두 처리돼야 머지할 수 있습니다. 실제 문제는 수정하고, 오탐이거나 의도된 동작이면 근거를 남긴 뒤 스레드를 닫습니다. 후속 커밋에서 문제가 해결됐다고 확인되면 지적이 자동으로 해소되기도 합니다. 수정 에이전트가 작업을 맡아 다음 리뷰까지 진행하는 경우도 있습니다. 원문

④ CI가 실행 결과로 머지를 통제

린트, 타입 검사, 플랫폼별 테스트, 빌드가 필수 검사입니다. CLI PR 하나에 사람이 보기 전에 수십 개 검사가 실행될 수 있습니다. PR 템플릿에는 어떻게 테스트했는지, 위험은 무엇인지, 어떻게 되돌릴지 적습니다. 에이전트가 내용을 작성해도 변경을 지시한 사람이 확인합니다. 원문

판정 규칙이 명확한 항목은 실행 가능한 검사에 맡길 수 있습니다. 예를 들어 포맷과 금지된 의존성은 린터나 정책 검사로 확인합니다. 재시도 조건이 제품 의도와 맞는지, 실패 상태에서 사용자가 복구할 수 있는지는 코드 관계와 요구사항을 읽어야 합니다.

⑤ 변경 위험도에 따른 사람 승인

위험도원문의 예사람 승인
낮음문서, 문구, 내부 전용 기능, 플래그 뒤에 추가한 기능자동 리뷰와 필수 검사를 통과하면 0명 가능
중간일반 제품 변경, 캐시·자동 업데이트·시스템 프롬프트 등 민감한 영역의 변경1명
높음가장 위험한 변경과 항상 두 명을 요구하도록 지정된 일부 경로2명

첫 번째 분류기는 변경 내용을 보고 등급을 매깁니다. 두 번째 분류기는 그 등급의 기본값보다 사람을 더 투입해야 하는지 확인합니다. 코드 소유자가 민감하다고 지정한 경로나 CI 워크플로에는 별도의 사람 승인 규칙이 적용됩니다. 간소화된 경로는 저장소의 신뢰 목록에 있는 작성자에게 적용됩니다. 에이전트가 작성한 PR은 작업을 지시한 사람이 책임지며, 내부 정책상 필요한 승인 인원에 포함될 수 있습니다. 사람 승인 요건은 사람이 충족합니다. 원문

승인은 특정 커밋을 대상으로 합니다. 승인 후 에이전트가 새 코드를 푸시하거나 사람이 충돌을 수동으로 해결해 시스템이 보증하기 어려운 커밋이 생기면 재승인을 받습니다. 같은 PR 번호에서도 검토한 코드와 머지될 코드가 달라질 수 있기 때문입니다. 원문

⑥ 머지 큐와 단계적 배포

PR A와 B가 각각 CI를 통과해도 같은 main에 합친 상태에서 문제가 생길 수 있습니다. 예컨대 A가 전송 실패 이벤트 발생 시점을 바꾸고 B가 그 이벤트를 받는 UI 상태 전이를 바꾸면, 두 변경이 만났을 때만 문제가 나타날 수 있습니다. 머지 큐는 변경이 적용된 통합 상태에서 검사를 다시 실행합니다. 원문

새 동작은 보통 기능 플래그로 제어하고 직원이 먼저 사용합니다. 공개 배포는 latest가 먼저, stable이 뒤따릅니다. 머지 큐는 통합 코드, 사내 사용은 실제 사용 중 드러나는 회귀, 단계적 배포는 문제가 생겼을 때의 노출 범위를 다룹니다. 원문

⑦ 배포 후 탐지와 복구

텔레메트리, revert·장애 대시보드, 작성자, 주간 온콜 로테이션으로 문제를 찾습니다. 상황에 따라 기능 플래그를 끄거나 커밋을 되돌리거나 수정 버전을 배포합니다. 사고 리뷰에서는 어느 검증 단계에서 문제를 잡을 수 있었는지를 살핍니다. 글 공개 시점에는 revert나 장애 지표가 악화될 때 승인 요건을 자동으로 강화하는 서킷 브레이커가 아직 없었고, 팀은 사람 승인 없는 머지를 더 확대하기 전에 이를 원한다고 밝혔습니다. 원문

3. 밤새 50회 넘게 돈 리뷰 루프

한 CLI PR에서 리뷰 에이전트가 지적하고 작성 에이전트가 고치고 새 커밋이 다시 리뷰를 부르는 과정이 하룻밤에 50회 이상 반복됐습니다. 작성자가 개입해 멈췄습니다. git blame으로 확인하니 지적된 코드의 약 59%가 첫 리뷰 시점부터 이미 있었습니다. 여기에는 PR의 첫 버전에 이미 있던 코드도 포함됩니다. Pre-existing은 PR 이전부터 있던 버그를 가리키므로 기준 시점이 다릅니다. 원문

매번 전체 PR을 읽으면 리뷰어가 처음 놓쳤던 문제를 다음 라운드에서 조금씩 꺼낼 수 있습니다. 작성 에이전트는 사람이면 넘길 사소한 지적도 수정 대상으로 받아들이기 쉽습니다. 작은 지적 하나가 커밋, CI, 재리뷰를 다시 부르면 역할별 작업이 진행되는 동안 전체 리뷰는 끝나지 않을 수 있습니다.

변경반복을 줄이는 방식
3라운드 후 작성자에게 재검토 요청자동 수정이 이어져도 해결되지 않으면 사람이 접근법을 다시 봅니다. 미해결 문제는 해당 스레드나 필수 검사에서 계속 처리합니다.
초반 이후 새 diff 중심으로 재리뷰후속 수정이 도입한 문제에 집중합니다. 기존 지적의 해소 여부는 해당 스레드에서 확인할 수 있습니다.
한 줄보다 버그 유형을 지적한 곳의 취소 누락을 고칠 때 같은 전송 경로에 해당 유형의 누락이 더 있는지 함께 봅니다.
이미 게시한 지적은 반복 게시하지 않음같은 지적을 새 작업으로 받아 또 커밋을 만드는 일을 줄입니다.

4. 운영 장애를 리뷰어의 평가 사례로 돌려보낸다

과거 장애를 일으킨 PR과 해당 수정·revert를 모아, 코드를 아는 엔지니어가 실제 결함과 위치를 확인합니다. 후속 글에 따르면 당시 리뷰어가 볼 수 있었던 저장소 상태를 재현하고 결함을 설명하는 짧은 정답을 둡니다. 문제를 정확히 짚은 지적에 점수를 주고, 튜닝 데이터와 최종 평가에 쓰는 고정 데이터를 나눕니다. 팀은 매일 평가를 돌려 리뷰어 변경이 과거 결함 탐지에 어떤 영향을 주는지 봅니다. 원문 Fig. C · 검증에 관한 후속 글

평가 루프는 다음 순서로 돕니다.

  1. 장애·revert 발생 — 원인과 당시 코드를 확인합니다.
  2. 평가 사례에 추가 — 확인한 결함을 리뷰어 평가 데이터로 만듭니다. 정상적으로 머지된 PR도 함께 넣습니다.
  3. 리뷰어 정기 평가 — 프롬프트·도구·모델을 바꿀 때마다 같은 사례로 다시 평가합니다.
  4. 탐지율과 오탐 확인 — 과거 결함을 얼마나 잡는지, 정상 PR에 불필요한 지적을 얼마나 내는지 봅니다.
  5. 변경 채택 또는 재조정 — 결과에 따라 변경을 반영하거나 되돌리고, 다음 변경에서 3번으로 돌아갑니다.

안정적으로 머지된 정상 PR도 평가에 넣습니다. 장애 PR만 주면 리뷰어가 모든 PR에 많은 문제를 보고하는 쪽으로 튜닝되기 쉽습니다. 정상 사례를 함께 보면 오탐 중에서도 정상 동작을 잘못 고치게 만들 만큼 해로운 지적을 찾을 수 있습니다. 실제 코멘트에 대해서는 작성자가 수정했는지, 오탐이라고 판단했는지, 의도된 동작이라고 설명했는지, 중요하지 않다고 봤는지를 기록합니다. 수정 여부는 유용한 신호지만 작성 에이전트가 제안을 그대로 따를 수 있어 정답으로 쓰기에는 부족합니다. 원문

탐지율을 후보 생성 직후 → 검증 후 → 최종 게시로 나누면 처음부터 결함을 놓쳤는지, 검증 그룹이 진짜 결함을 탈락시켰는지, 마지막 정리에서 빠졌는지 파악할 수 있습니다. 결과에 따라 코드 컨텍스트를 보강하거나 해당 단계의 규칙을 조정합니다. 검증에 관한 후속 글

6. 공개 Code Review와 Anthropic 내부 머지 정책

공개 Code Review for Claude Code는 Team·Enterprise 조직이 GitHub 저장소에서 사용할 수 있는 관리형 리뷰 서비스입니다. PR에 인라인 지적, 요약, 체크 실행 결과를 남깁니다. 코드와 diff를 읽는 방식이므로 빌드·실행 증거는 CI나 별도 검증에서 만듭니다. 서비스의 체크는 지적이 있어도 실패 상태로 끝나지 않습니다. 미해결 스레드 차단, 위험도별 승인 수, 머지 큐, 배포 플래그는 팀의 저장소·배포 정책에서 적용합니다. Code Review 공식 문서 · 원문

Quick·Standard·Deep은 리뷰의 깊이·시간·비용 설정입니다. 내부의 Low·Medium·High는 변경 위험도와 사람 승인 요건을 결정합니다. 관리형 리뷰는 PR 생성 시, 푸시마다, 수동 요청 시 실행하도록 설정할 수 있습니다. 리뷰 비용에는 깊이, PR 규모와 실행 횟수가 영향을 줍니다. 로컬 /code-review, Claude Code GitHub Action, 자체 리뷰 서브에이전트는 실행 위치와 운영 방식이 다른 선택지입니다. Code Review 공식 문서 · 비용과 사용량 가이드

7. 사람의 판단과 팀의 지식 공유

사람은 무엇을 만들지, 위험한 경로를 어떻게 바꿀지, 다른 팀원이 따라 할 아키텍처 패턴을 승인할지, 검증 증거가 무엇을 커버하는지 판단합니다. 공개 Slack 채널에서 작업 방향을 공유하고, 과거 결정이나 더 간단한 접근이 제시되면 PR을 일찍 접거나 범위를 조정합니다. 머지한 사람이 작은 변경이나 중간 위험 변경의 수정을 보통 맡고, 사고 리뷰에서는 어떤 검증을 보강할지 살핍니다. 원문

코드 리뷰의 또 다른 역할은 코드베이스 지식의 공유입니다. 팀은 정형화된 프로세스 없이, 작업 직전에 Claude에게 특정 모듈의 현재 동작을 설명하게 하거나 작은 시각 자료를 만들어 활용합니다. 예컨대 새 팀원이 기기 페어링을 맡는다면, 등록 요청부터 연결 성공·실패까지 상태가 어떻게 바뀌는지 현재 코드에 근거해 설명하는 자료가 업무에 직접 도움이 됩니다. 원문

정리

CLAUDE.md와 harness-guide.md를 운용할 때 비교할 부분은 각 규칙이 어디에서 실행되는지, 어떤 증거가 남는지, 실패하면 누가 다음 결정을 하는지입니다. 예를 들어 전송 취소를 검증한다는 지침은 실행할 기기와 테스트, 남길 로그·상태, 자동 수정 루프 종료와 담당자 인계 조건까지 구체화하면 운영에 쓸 수 있습니다.
