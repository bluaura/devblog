1. 256GB 맥에서 쓸 수 있는 로컬 LLM

256GB 중 모델에 쓸 수 있는 메모리는 약 218GB다. 오픈웨이트 최상위권 모델은 여기에 들어가지 않는다.

256GB에 안 들어가는 모델

GLM-5.3(753B), DeepSeek V4 Pro(1.6T), Kimi K3(2.8T), MiMo-V2.6-Pro(1.02T), Hunyuan Hy4는 모두 300GB 이상이 필요하다. DeepSeek V4.1 Flash도 512GB급 후보로 분류된다.

  • 같은 모델을 6/8bit로 올리면 메모리 초과로 프로세스가 종료된 사례가 있다. 4bit가 현실적 상한이다.

3. 에이전트를 만들 때 중요한 LLM 능력 (코딩 제외)

가장 중요한 것은 툴 호출 신뢰성이다. 에이전트는 여러 단계를 연속 실행하므로 단계별 오류가 곱으로 누적된다. 단계당 성공률 95%면 20단계 작업 성공률은 약 36%이고, 99%면 약 82%다.

  1. 툴 호출 신뢰성: 올바른 툴 선택, 스키마에 맞는 인자, 깨지지 않는 JSON. 양자화하면 이 부분이 먼저 무너지는 경우가 많다.
  2. 지시 준수와 장기 작업 안정성: 수십 턴이 지나도 시스템 프롬프트의 규칙을 지키는 능력. 파일 삭제나 메일 전송처럼 되돌릴 수 없는 동작과 직결된다.
  3. 오류 복구와 멈출 줄 아는 판단: 툴 실패 시 같은 호출을 반복하지 않고, 불확실할 때 지어내지 않고 묻는 능력.
  4. 긴 컨텍스트 활용: 쌓이는 툴 결과 속에서 필요한 정보를 정확히 찾는 능력. 맥에서는 프롬프트 처리 속도도 같이 본다.
  5. 화면 이해: 앱을 직접 조작한다면 필수. AppleScript, 단축어, MCP, CLI 중심 설계면 우선순위가 내려간다.
  6. 속도: 한 작업에 호출이 수십 번이라, 충분히 똑똑하고 빠른 모델이 유리한 경우가 많다.

공개 벤치마크는 원본 정밀도 기준이므로, 실제 쓸 툴 10~20개로 자체 테스트 세트를 만들어 양자화 모델의 호출 성공률을 재는 것이 가장 정확하다.

클라우드와의 격차

  • 짧은 작업: OSWorld-Verified 기준 Claude Opus 5가 83.4%, Gemini 3.7 Flash가 83.0%이고 Holo 3.1이 82.56%로 비슷하다.
  • 긴 워크플로: OSWorld 2.0(108개 장기 작업)에서는 GPT-6 Astra 72.6%, Claude Opus 5 70.6%인데 오픈웨이트 최고가 19.4%다.

맥 에이전트 설계 시 참고

  • 화면만 보지 말고 손쉬운 사용(Accessibility) API의 요소 트리를 같이 쓴다. 좌표 추정 오류가 크게 줄어든다.
  • 클릭보다 명령을 우선한다. Qwen-UI-Agent 논문에서 가장 어려운 데스크톱 벤치마크 동작의 55.1%가 타이핑 명령이었다.
  • 긴 작업은 5~10단계 단위로 쪼개고 단계마다 결과를 검증한다.
  • 계획은 큰 모델, 좌표 찾기는 작은 전용 모델로 나누는 2모델 구성도 가능하다.

벤치마크는 대부분 Ubuntu·Android·웹 환경 기준이라 macOS 성능은 직접 측정된 것이 아니다. 집계 사이트마다 오픈웨이트 표기가 엇갈리는 모델도 있으므로 라이선스는 받기 전에 확인한다.

5. iOS 자동 테스트 설계: 조작은 LLM, 판정은 코드

LLM이 "성공했다"고 스스로 보고하는 것을 판정 기준으로 쓰면 신뢰할 수 없다. 조작과 판정을 분리한다.

구조

  1. 테스트 케이스 정의: Given/When/Then 형식. Then은 기계가 확인할 수 있는 조건으로 적는다.
  2. 기기 제어 계층: XCUITest 또는 WebDriverAgent를 감싸 tap, type, swipe, launch, waitFor 같은 툴로 노출한다.
  3. 관찰: 접근성 요소 트리가 기본, 스크린샷은 보조.
  4. 판정기(오라클): 에이전트와 별도 모듈. 에이전트가 끝났다고 한 뒤 독립적으로 조건을 검사한다.
  5. 리포트: 단계별 스크린샷, 요소 트리, 로그, 영상을 남기고 JUnit XML로 출력한다.

판정 방법의 우선순위

  • 1순위, 결정적 검증: UI 요소의 존재·값, 앱 로그, 앱 컨테이너의 파일·DB, 네트워크 요청, 서버 상태.
  • 2순위, 스냅샷 비교: 기준 스크린샷과의 차이.
  • 3순위, LLM 시각 판정: 위 방법으로 안 되는 것에만. 조작한 모델과 다른 호출로 분리한다.

결과 구분

결과 의미
PASS / FAIL 앱이 기대대로 동작했는지 여부
BLOCKED 에이전트가 화면을 못 찾았거나 환경 문제로 검증까지 못 간 경우
FLAKY 재실행 시 결과가 바뀌는 경우

BLOCKED를 FAIL과 섞으면 앱 버그와 에이전트 실수를 구별할 수 없다.

안정성을 위한 설계

  • 매 케이스 초기화: 앱 재설치, 고정된 로케일·시간, 목 서버, 애니메이션 끄기.
  • 기록 후 재생: LLM이 한 번 성공한 경로는 스크립트로 저장해 LLM 없이 재생하고, 재생이 깨질 때만 LLM을 부른다.
  • 한도 설정: 케이스당 최대 단계 수와 시간 제한.

기기 간 연동 기능을 테스트한다면

  • 시뮬레이터는 Bluetooth를 지원하지 않으므로 실기기가 필요하다.
  • 판정을 양쪽에서 한다. 파일 전송은 iOS 화면의 완료 표시만이 아니라 상대 기기에 도착한 파일의 해시까지 비교한다.
  • 연결 끊김, 권한 거부 같은 실패 상황은 테스트용 실행 인자나 훅으로 주입한다.

6. 맥에 연결한 아이폰에서 빌드·실행·테스트하기

iOS에서는 Xcode에 포함된 xcodebuild와 devicectl이 adb 역할을 한다.

사전 준비

  1. 아이폰을 케이블로 연결하고 "이 컴퓨터를 신뢰" 승인.
  2. 설정 > 개인정보 보호 및 보안 > 개발자 모드 켜기(재부팅 필요).
  3. Xcode에서 Apple 계정으로 서명 팀 설정. 무료 계정은 앱이 7일 뒤 만료된다.
  4. 이후에는 같은 네트워크에서 무선 연결도 가능하다.

사용하게 되는 기술

계층 기술 역할
빌드·테스트 실행 xcodebuild 빌드, 서명, 설치, 테스트 실행, 결과 번들 생성
기기 관리 devicectl 기기 목록, 앱 설치·삭제·실행, 파일 복사, 프로세스 조회
UI 조작 XCUITest 탭·입력·스와이프, 요소 조회, 스크린샷

xcodebuild

terminal
# 빌드 후 실기기에서 테스트 실행
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS,id=<UDID>' \
  -allowProvisioningUpdates \
  -resultBundlePath out.xcresult

# 결과를 JSON으로 추출
xcrun xcresulttool get test-results summary --path out.xcresult
  • 주요 동작: build, test, build-for-testing, test-without-building.
  • 대상 확인: xcodebuild -showdestinations -scheme <스킴>.
  • 케이스 선택: -only-testing:타깃/클래스/메서드, -skip-testing:, -testPlan.
  • 불안정 테스트 대응: -retry-tests-on-failure, -test-iterations <N>.
  • 종료 코드가 0이면 전체 통과다.

devicectl

Xcode 15에서 도입됐고 iOS 17 이상 기기를 지원한다.

terminal
xcrun devicectl list devices
xcrun devicectl device install app --device <ID> MyApp.app
xcrun devicectl device process launch --device <ID> --console <번들ID>
xcrun devicectl device copy from --device <ID> \
  --domain-type appDataContainer --domain-identifier <번들ID> \
  --source Documents/result.json --destination ./result.json
  • 기기: list devices, device info details, device info lockState, device reboot, manage pair.
  • 앱: device install app, device uninstall app, device info apps.
  • 프로세스: device process launch, device info processes.
  • 파일: device copy from/to, device info files.
  • 자동화용 출력: --json-output <파일>.
  • 한계: 스크린샷, UI 입력, 시스템 전체 로그 스트림이 없다. 폴더 단위 재귀 복사도 안 된다.

세부 옵션은 Xcode 버전에 따라 다르므로 xcrun devicectl help와 man xcodebuild로 확인한다. 위 명령 예시는 문서 기준으로 정리한 것이며 직접 실행해 검증하지는 않았다.

포트 포워딩 adb forward pymobiledevice3 usbmux forward, iproxy
무선 연결 adb tcpip Xcode의 "Connect via network"
재부팅 adb reboot devicectl device reboot
셸 adb shell 없음

7. 맥용 테스트 프로그램으로 아이폰 앱을 테스트할 수 있는가

가능하다. UI 조작 명령은 아이폰 안에서 도는 테스트 러너 앱이 실행해야 하므로 "맥의 지휘 프로그램 + 아이폰의 러너" 구조가 된다.

  • 방식 A, xcodebuild 지휘형: 테스트를 Swift XCUITest로 작성하고, 맥 프로그램이 xcodebuild test를 호출해 xcresult를 읽는다. 가장 단순하고 안정적이다.
  • 방식 B, 실시간 조작형: 러너가 아이폰에서 HTTP 서버를 띄우고(WebDriverAgent), 맥이 포트 포워딩으로 명령을 보낸다. LLM 에이전트가 화면을 보며 탐색하려면 이 방식이 필요하다.
  • 소스 없는 앱도 XCUIApplication(bundleIdentifier:)로 대상으로 삼을 수 있다. 서명이 필요한 것은 러너 쪽이다.
  • Appium 문서에 따르면 iOS 27부터는 devicectl로 WDA를 띄우는 방식이 막혀 xcodebuild나 RemoteXPC 터널로 시작해야 한다.

화면 인식인가, ID인가

기본은 ID 기반이다. XCUITest는 접근성 요소 트리를 조회하며 화면 픽셀을 분석하지 않는다.

TransferTests.swift
let app = XCUIApplication()
app.launch()

let send = app.buttons["sendButton"]   // accessibilityIdentifier로 조회
XCTAssertTrue(send.waitForExistence(timeout: 10))
send.tap()

XCTAssertTrue(app.staticTexts["transferDone"].waitForExistence(timeout: 30))
  • 앱 코드에서 accessibilityIdentifier를 달아두는 것이 가장 안정적이다. 문구나 언어가 바뀌어도 깨지지 않는다.
  • 요소 종류, 표시 텍스트, 조건식으로도 찾을 수 있다.
  • 게임, 캔버스, 접근성 정보가 없는 커스텀 뷰는 스크린샷과 좌표 탭으로 처리해야 하고, 여기에 비전 모델을 붙일 수 있다.

포그라운드, 유선, 백그라운드 제약

  • 대상 앱은 포그라운드여야 조작된다. app.launch()나 app.activate()가 앱을 앞으로 가져온다.
  • 러너는 백그라운드 제약을 받지 않는다. 테스트 세션 동안 시스템 테스트 데몬의 지원을 받아 살아 있고, 대상 앱이 앞에 있는 동안 뒤에서 이벤트를 주입한다.
  • 백그라운드 전환도 테스트된다. XCUIDevice.shared.press(.home)으로 홈으로 보내고 app.state로 .runningBackground 여부를 확인한 뒤 다시 activate()할 수 있다.
  • 유선은 최초 페어링에만 필수다. 무선도 되지만 자동 테스트에는 유선이 안정적이다.
  • 기기는 잠금 해제 상태여야 한다. 자동 잠금을 끈다.
  • 러너와 대상 앱은 별도 프로세스라 앱 내부 상태를 직접 읽을 수 없다. 실행 인자, 로그, 컨테이너 파일로 확인한다.
