끝났는지 확인할 수 있어야 '작업 하나'다

1회차에서는 입력·변경 범위·기대 동작·완료 증거를 적는 작업 계약을 다뤘다. 이번에는 그 계약이 조금 커졌을 때, 확인 가능한 작은 계약들로 나누는 방법을 다룬다. 1회차 코드를 작성하지 않았어도 진행할 수 있다.

동료에게 인계할 수 있는 크기를 떠올린다

동료에게 "파일 전송 화면 완성"을 맡기면 전송 자체·진행률·오류 표시까지 여러 판단이 섞인다. "정상 입력을 받으면 정해진 진행률 문구가 나오는 부분"을 맡기고 입력 예시까지 붙이면, 그 동료가 남긴 결과를 확인하기 쉬워진다.

에이전트도 같다. 프롬프트는 작업의 내용을 전달하고, 모델은 구현 방법을 판단한다. 하네스는 선택한 작업의 문맥·도구·검사 결과를 연결한다. 이번에 만드는 작업 목록은 그 하네스가 참조할 명세이며, 목록만 썼다고 자동으로 순서가 제어되거나 검증이 강제되지는 않는다.

왜 작은 단위가 도움이 되나

요청에 여러 동작이 섞여 있으면 일부만 구현된 상태에서 무엇이 남았는지 파악하기 어렵다. 각 작업에 확인 기준을 붙이면 실패한 범위를 좁혀 볼 수 있고, 다음 작업에 넘길 결과도 분명해진다. 다만 지나친 분해는 설명과 인계 부담을 늘리므로 "작을수록 무조건 좋다"는 규칙으로 쓰지 않는다.

근거와 적용을 구분한다 — Anthropic은 큰 과제를 하위 과제로 나누고 중간 결과를 검사하는 구성 패턴을 설명한다. [1] 별도의 장시간 코딩 실험에서는 기능별 목록을 두고 한 번에 한 기능에 집중하는 방식을 사용했다. [2] 아래의 두 작업 분해와 카드 양식은 이를 앱 개발 교육에 적용한 예시이며, 업체의 고정 표준은 아니다.

기능을 '동작과 증거'로 나눈다

오늘의 예시는 전송 바이트 수를 받아 상태 문구를 만드는 기능이다. 파일을 보내는 네트워크 코드나 실제 화면은 다루지 않는다.

큰 기능 → 확인 가능한 두 작업 → 전체 확인

단계내용예시 입력 → 결과증거
상위 목표전송 상태 요약 문구 만들기sent, total → 상태 문자열아래 전체 확인으로 판단

전체 확인상위 목표의 수용 기준 확인정상·완료·오류 문구를 같은 함수에서 확인최종 코드 기준 결과. 일부 작업의 통과와 전체 기능의 완료는 구분

분해 구조를 설명하는 표다. 두 작업의 병렬 실행이나 자동 완료 판정을 의미하지 않는다.

읽는 순서

  1. 상위 목표를 유지한다. 사용자가 얻으려는 결과는 "상태 문구"다. 분해하면서 새 전송 기능을 추가하지 않는다.
  2. 동작 경계를 정한다. T1은 정상 입력, T2는 잘못된 입력을 책임진다. 각 작업의 입력 예시와 예상 출력이 따로 있다.
  3. 각 작업 안에 검증을 넣는다. "코드 작성"과 "언젠가 테스트"를 떼어 두기보다, 구현과 그 동작의 확인을 함께 맡긴다.
  4. 최종 상태를 다시 본다. T2를 구현하다 T1을 깨뜨릴 수 있다. 각 작업의 과거 통과 기록만 모으지 말고, 마지막 코드에서 전체 사례를 확인한다.

이 예에서는 두 작업이면 충분하다. 작업 수를 3개나 5개로 맞추는 것이 목표는 아니다. 서로 확인 가능한 작업이라고 해서 서로 영향을 주지 않는 것은 아니며, 실행 순서와 선행 조건은 다음 회차에서 자세히 다룬다.

각 작업에 작은 계약을 붙인다

상위 계약 · 교육용 명세

string BuildTransferSummary(long sent, long total)가 상태 문자열을 반환한다. 정상 입력은 total > 0, 0 ≤ sent ≤ total이다. 진행 중에는 백분율의 소수점을 버리고, 완료 상태는 별도 문구로 표시한다.

정상 범위를 벗어난 입력은 전송 정보 오류를 반환한다. 계산 함수가 예외를 던지도록 정했던 1회차와 달리, 이번 것은 사용자에게 보여 줄 요약 문자열을 만드는 상위 기능이다. 기존 계산 함수의 계약을 바꾼다는 뜻은 아니다.

0바이트 파일을 위한 제품 정책은 별도로 정할 수 있다. 이 실습에서는 total = 0을 오류 입력으로 고정했다. 대용량 long 입력에서도 중간 계산이 넘치지 않아야 한다.

작업 카드 두 장

두 카드 모두 시작 상태는 미실행이다. 사용자가 실행했거나 사례가 통과했다는 기록이 아니다.

항목T1 · 정상 입력의 상태 문구 만들기T2 · 잘못된 입력을 오류 문구로 처리하기
목적정상 전송량이 들어오면 진행 또는 완료 문구가 나온다.잘못된 입력이 계산 단계로 흘러가지 않고 오류 문구로 처리된다.
범위상태 문구 함수와 정상 입력 검증 코드. UI·통신·파일 입출력은 제외.입력 경계 처리와 그 검사. 기존 정상 동작을 유지한다.
산출물작은 함수 변경과 정상·완료 사례의 실제 결과. T1 단계에서 오류 입력 처리가 미구현이면 명시한다.오류 입력 처리 변경과 오류 사례 결과, 같은 최종 코드에서 정상 사례를 다시 확인한 결과.
수용 기준"이 작업의 결과를 받아들일 조건"이다. 아래 T1 행의 출력과 정확히 일치해야 한다.아래 T2 행이 모두 오류 문구를 반환하고, T1 행도 계속 통과한다.

얼마나 작게 나누면 될까

작업 크기는 파일 수나 코드 줄 수만으로 판단하기 어렵다. 먼저 한 번의 변경 뒤에 어떤 결과를 보여 줄 수 있는지 묻는다. 아래 세 가지를 비교하면 경계가 보인다.

판단작업 예이유조치
너무 넓음연동 앱의 파일 전송 전체 완성연결·전송·화면·오류가 함께 섞인다.무엇을 확인해야 완료인지 카드 하나에 담기 어렵다면 결과를 더 좁힌다.
이번 실습에 적절정상 입력의 상태 문구 생성(1,3) → 진행 중 33%라는 명확한 결과가 있다.정해진 동작의 구현과 검증을 함께 맡길 수 있다.
보통은 너무 작음지역 변수 하나 선언기능의 기대 결과를 직접 보여 주기 어렵다.별도 의미가 없다면 주변의 동작 단위와 합쳐 인계 부담을 줄인다.

오늘 과제에 대한 교육용 판단이다. 변수명 변경 자체가 목표인 리팩터링 등에서는 작은 변경도 별도 작업이 될 수 있다.

분해를 멈출 때의 세 가지 질문

  1. 입력과 기대 결과를 한두 문장으로 설명할 수 있나? "문구를 예쁘게"보다 정확한 문자열이나 확인할 화면 조건이 낫다.
  2. 증거를 지금 얻을 수 있나? 외부 장치가 없다면 순수 계산·문구 생성처럼 로컬에서 확인할 부분을 먼저 잡을 수 있다. 이것으로 실제 전송을 검증했다고 보지는 않는다.
  3. 분리한 이득이 있나? 작업 카드만 늘고 결과를 따로 확인할 수 없다면 다시 합친다.
작업 목록을 바꾸어도 될 때 — 저장소를 읽어 보니 가정했던 함수가 없거나 수정 범위가 예상보다 크다면, 확인한 사실을 근거로 카드를 조정할 수 있다. 실패한 검사를 없애 완료로 보이게 만드는 것과는 구분한다.

25분 실습

두 장의 작업 카드를 만들고, 하나만 실행한다.

준비물: Claude 또는 Codex, 작업 메모, 선택적으로 수정 가능한 작은 C# 프로젝트와 실행 환경. 새 프레임워크나 패키지는 필요하지 않다.

  1. 0~5분 · 상위 목표를 적는다. "바이트 수를 받아 진행·완료·오류 문자열을 만든다"를 적고, 위 예상값 표를 계약으로 고정한다. 1회차 계산 함수가 없어도 시작할 수 있다.
  2. 5~10분 · 작업 두 개로 나눈다. T1·T2를 각 카드에 적는다. 목적·변경 범위·산출물·수용 기준을 채운다. 제목만 두 줄 쓰는 것으로 끝내지 않는다.
  3. 10~13분 · 분해를 검토한다. 에이전트에게 카드의 빠진 동작과 중복 범위를 찾아 달라고 한다. 각 예상값 행이 어느 카드에 포함되는지 대응시킨다.
  4. 13~22분 · T1만 구현하고 확인한다. 아래 요청문으로 T1의 정상 입력 동작을 구현하고 검사한다. T2는 아직 미구현일 수 있으므로 전체 기능이 끝났다고 표시하지 않는다.
  5. 22~25분 · 증거와 남은 범위를 기록한다. 실행 명령·결과와 변경 내역을 확인하고, "T1: 확인한 범위 / T2: 남은 범위"를 한 줄씩 적는다. 시간이 끝나도 실패나 미실행을 통과로 바꾸지 않는다.
기대 산출물 — 상위 계약 1개 + 작업 카드 2개 + T1의 변경·실행 근거 + T2의 남은 범위 메모.

저장소·실행 환경이 없다면 같은 과제로 카드와 예상값 표를 완성하고, 각 작업의 검사 방법을 문장으로 적는다. 에이전트에게 누락 여부를 검토받을 수 있지만, 구현·실행 상태는 '미실행'으로 남긴다. 이 경로에서는 작업 분해를 연습한 것이며 코드 검증을 마친 것이 아니다.

바로 쓰는 요청문

Claude와 Codex에 보낼 수 있는 요청문이다. 작업을 나누어 검토하고 T1만 실행하도록 범위를 정한다. 실제 작업 카드 양식은 자유롭게 바꿔도 된다.

task-decomposition-prompt.txt
프로젝트 구조와 지침을 읽고, 아래 기능을 검증 가능한 작업으로 나눠 검토해 줘.

상위 기능
C# string BuildTransferSummary(long sent, long total)
정상 입력: total > 0, 0 <= sent <= total.
진행 중: "진행 중 N%" (N은 백분율 소수점 버림).
sent == total: "전송 완료 100%".
잘못된 입력: "전송 정보 오류".
long 큰 값에서도 중간 계산 오버플로가 없어야 한다.

작업 초안
T1: 정상 입력의 진행·완료 문구와 검증.
T2: 잘못된 입력을 오류 문구로 처리하고 T1 재검증.
각 카드의 목적·범위·산출물·수용 기준을 적고,
빠진 동작과 중복 범위가 있으면 근거와 함께 조정해 줘.

이번 실행 범위
T1만 구현·검증해 줘. T2는 남은 작업으로 명시해 줘.
T1 검사:
(0,100) → "진행 중 0%"
(50,100) → "진행 중 50%"
(1,3) → "진행 중 33%"
(100,100) → "전송 완료 100%"
(long.MaxValue,long.MaxValue) → "전송 완료 100%"
(long.MaxValue-1,long.MaxValue) → "진행 중 99%"

UI·통신·파일 입출력은 바꾸지 말고 기존 검증 도구를 우선 사용해 줘.
변경 파일·diff 요약·실제 실행 명령·사례별 결과를 보고해 줘.

요청문에서 "이번 실행 범위" 아래를 지우고 "구현은 하지 말고 작업 카드와 예상값 대응표만 작성해 줘"로 바꾼다. 목적은 작은 작업의 경계를 설계하는 것이다.

결과 확인 체크리스트

  • 각 작업 카드에 목적·범위·산출물·수용 기준이 있다. "계산 구현"처럼 제목만 있는 카드는 보완했다.
  • 상위 계약의 모든 예상값 행이 T1 또는 T2에 대응된다. 정상 입력만 분해하고 오류 처리를 빠뜨리지 않았다.
  • T1을 실행했다면 실제 입력과 출력의 일치를 검사했다. 숫자나 문자열을 출력만 하는 것으로 통과를 판단하지 않았다.
  • 변경 파일과 diff를 보고 UI·통신 등 범위 밖 수정이 없는지 확인했다. 실행 경로를 택하지 않았다면 이 항목도 미검증으로 남겼다.
  • T1의 통과·실패·미실행을 근거와 함께 기록했고, 미구현인 T2를 완료로 표시하지 않았다.
  • 전체 기능 완료 시 최종 코드에서 정상·완료·오류 사례를 모두 다시 확인해야 함을 작업 메모에 남겼다.

이 목록은 활동 순서를 보여 주지만, 어떤 동작이 구현됐는지 말해 주지는 않는다. 이번 실습에서는 "정상 문구가 나온다", "잘못된 입력에 오류 문구가 나온다"로 나누고, 각 동작 안에 구현과 확인을 함께 넣는다.

계층별 작업이나 별도 테스트 작업이 항상 잘못된 것은 아니다. 그 경우에도 산출물과 인수 조건이 구체적이어야 한다. 이번 회차는 작은 앱 기능에서 동작을 기준으로 자르는 연습이다.
