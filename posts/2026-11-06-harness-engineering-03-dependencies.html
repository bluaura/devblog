필요한 결과가 준비되어야 시작할 수 있다

2회차에서는 전송 상태 문구 기능을 정상 입력과 오류 입력에 대한 작은 작업으로 나눴다. 이번에는 그 작업을 진행할 때 어떤 결과를 먼저 받아야 하는지 정한다. 이전 실습 완료 여부와 관계없이, 아래 교육용 명세로 시작할 수 있다.

요리로 생각해 보면

밥을 담을 그릇을 꺼내는 일은 밥이 다 되기 전에도 할 수 있다. 밥을 그릇에 담는 일은 지어진 밥과 준비된 그릇이 모두 있어야 한다. 단순히 목록에서 앞에 적혔다는 이유와, 실제 결과가 필요해서 기다리는 이유를 구분하는 것이 의존성 설계의 출발점이다.

하네스에서 무엇이 달라지나

프롬프트는 이번 작업의 목표와 조건을 전달한다. 모델은 그 조건을 해석해 코드를 만들거나 도구를 고른다. 하네스는 정의된 조건에 따라 작업을 선택하고 선행 결과를 전달하는 역할을 맡을 수 있다. 문서에 화살표를 그리는 단계와, 이를 코드로 강제하는 단계는 구분해서 생각한다.

이번 회차에서는 자동 실행기를 만드는 대신, 하네스가 판단할 수 있을 만큼 "무엇이 있어야 시작할 수 있는가"를 구체화한다. 실제 도구의 설정과 연결하는 것은 뒤 회차에서 확장한다.

실무에서 보이는 같은 원리 — GitHub Actions는 needs로 선행 작업을 지정하며, 기본적으로 그 작업들이 성공해야 후속 작업을 실행한다. [1] 코딩 에이전트에도 "앞 작업의 출력이 다음 작업의 입력이 된다"는 구성을 적용할 수 있다. [2] 이번 표는 그 원리를 설명하는 교육용 설계다.

의존 관계에 반드시 붙일 두 가지

  • 필요한 산출물 — 예를 들어 함수 이름과 반환 형식이 적힌 계약, 구현 파일, 검사 코드다.
  • 인수 조건 — 그 산출물을 다음 작업에 넘겨도 되는 기준이다. 파일이 존재하는지만 볼지, 명세 항목이 채워졌는지까지 볼지를 정한다.

"A 완료" 한 줄보다 "A의 함수 명세가 있고 필수 항목이 채워져 있다"가 후속 작업의 시작 근거로 더 분명하다. 작업별 인수 조건은 전체 기능을 최종 검증했다는 뜻과 같지 않다.

전송 상태 문구 기능을 연결해 보기

2회차 기능을 같은 이름으로 유지하되, 이번에는 산출물을 주고받는 관점에서 A~D로 다시 묶는다. 이전 T1·T2의 정상·오류 동작은 B와 C의 범위 안에 모두 포함된다.

두 갈래의 준비 결과가 모여야 전체 검사를 실행한다

작업내용받는 것내놓는 것확인할 점
A · 명세 고정함수 계약과 예상값 표교육용 상위 요구사항입력·출력·오류 정책대상 기능과 변경 범위를 읽을 수 있음
B · 구현 준비상태 문구 함수 작성A의 계약구현 소스검사에 연결할 함수가 존재하고, 빠진 분기가 없는지 검토
C · 검사 준비예상값 비교 코드 작성A의 계약검사 소스정상·완료·오류 사례와 실패 판정이 있는지 검토
D · 전체 확인함수와 검사 코드를 연결해 실행B의 함수 + C의 검사 코드 (둘 다 필요)실행 명령·실제 출력·사례별 결과실행 도구와 환경이 준비됨

표의 관계는 실행에 필요한 산출물의 전달 관계다. 이 글이 실제 에이전트나 CI 작업을 실행하지는 않는다.

화살표를 하나씩 읽기

  1. A → B — 구현할 함수의 입력·출력 계약이 필요하다. "오류를 예외로 던질까, 문구로 반환할까?"를 구현자가 추측하게 두지 않는다.
  2. A → C — 예상 출력과 함수 모양이 정해지면, 구현이 완성되기 전에도 검사 소스를 설계할 수 있다. 이 단계에서는 실제 통과를 주장하지 않는다.
  3. B·C → D — 실행할 함수와 검사 코드가 모두 필요하다. 한쪽만 준비되면 전체 검사를 시작할 재료가 부족하다.

여기에는 B → C가 없다. 이번 C의 범위는 계약을 기준으로 검사 소스를 작성·검토하는 데까지이기 때문이다. C에 "실제 실행까지"를 포함한다면 B의 구현도 필요해진다. 의존성은 작업의 이름만으로 정해지지 않고, 정한 범위에 따라 달라진다.

B와 C 사이에 결과 의존성이 없다고 해서 같은 저장소에서 언제나 병렬 실행해도 된다는 뜻은 아니다. 같은 파일을 수정하는 등 충돌 조건도 살펴야 한다. 이번에는 한 작업씩 진행해도 충분하다.

"앞 작업" 대신 "필요한 결과"를 적는다

이번에도 같은 교육용 기능을 사용한다

string BuildTransferSummary(long sent, long total)

  • 정상 범위: total > 0, 0 ≤ sent ≤ total
  • 진행 중: 진행 중 N% — 백분율 소수점 버림
  • 완료: 전송 완료 100%
  • 범위 밖 입력: 전송 정보 오류

실제 프로젝트를 진단한 명세가 아니다. 1회차의 내부 계산 함수와 2회차부터의 사용자용 요약 함수는 오류 표현의 계약이 다르다. 이번에는 2회차의 요약 함수 계약을 유지한다.

이번 의존성 연습을 위한 최소 사례다. 실제 구현을 검증할 때는 2회차의 음수·큰 long 입력 등 전체 사례도 유지해야 한다. 표에 적었다는 사실은 실제 실행의 증거가 아니다.

선행 결과가 하나 빠지면 어떻게 될까

준비된 산출물에 따라 D의 시작 가능 여부가 달라진다. 실행 환경은 준비됐다고 가정한 조건 판단이며, 실제 저장소·에이전트·테스트 상태를 읽은 결과가 아니다.

상황D 판정다음에 할 일이유
명세 A도 아직 준비되지 않음시작 조건 미충족B와 C 모두 A의 계약을 기다린다.D는 B의 구현과 C의 검사 코드가 필요하다. 먼저 A의 명세를 준비해야 한다.
A만 준비됨시작 조건 미충족B와 C의 소스 작성은 시작할 수 있다.D에 필요한 두 산출물이 아직 없다.
A·B 준비, C 없음시작 조건 미충족C의 검사 소스 준비가 필요하다.B만으로는 전체 검사를 실행할 수 없다. C가 인수 조건을 충족해야 한다.
A·B 준비, C 파일은 있지만 비교 검사가 빠짐시작 조건 미충족C의 검사 소스 준비가 필요하다.파일이 있어도 인수 조건을 충족하지 않으므로 C는 준비된 것이 아니다.
A·B·C가 인수 조건을 만족함시작 가능B의 구현과 C의 검사 코드가 모두 준비됐다.실행 환경이 준비됐다는 가정에서 D를 시작할 수 있다. 실제 실행과 통과가 이미 이루어졌다는 뜻은 아니다.

중요한 것은 '하나라도'가 아니라 '모두'다

D의 시작 조건은 B의 구현 준비 그리고 C의 검사 준비다. B가 준비됐다는 사실로 C의 검사 코드까지 생기지는 않는다. C 파일이 있어도 비교 검사가 없다면 이번에 정한 인수 조건을 만족하지 않는다.

반대로 C를 준비하는 작업은 A의 계약만으로 시작할 수 있으므로, B가 아직 없다는 이유만으로 계획에서 멈춰 둘 필요는 없다. 실제 실행 여부를 판단하는 D와 소스 작성 범위인 C를 구분했기 때문에 가능한 판단이다.

계획을 데이터로 적으면

이 글에서 만든 설명용 형식이다. 특정 도구가 자동으로 읽는 설정 파일은 아니다. requires의 각 항목은 모두 충족되어야 한다고 정의한다. 산출물의 세부 인수 조건은 앞의 표에 둔다.

plan.json
{
  "A": { "requires": [], "output": "함수 계약과 예상값 표" },
  "B": { "requires": ["A"], "output": "검토된 구현 소스" },
  "C": { "requires": ["A"], "output": "검토된 검사 소스" },
  "D": { "requires": ["B", "C"], "output": "실제 실행 결과" }
}

D에는 실행 도구·환경이라는 추가 시작 조건도 있다. 이 예시는 의존 관계의 모양만 보여 준다.

25분 실습

작업 네 개에 시작 조건을 붙인다.

준비물: 작업 메모와 Claude 또는 Codex. 저장소가 없어도 위 A~D 예시를 사용할 수 있다. 구현 순서를 설계하고 근거를 확인하는 연습이라 새 실행 환경을 설치하지 않아도 된다.

  1. 0~5분 · 작업과 결과를 적는다. A~D를 메모에 옮기고 각 작업이 내놓는 산출물을 한 줄씩 적는다. 기존 저장소에 적용한다면 함수·명세·검사 파일 등 실제 확인한 이름을 사용한다.
  2. 5~10분 · 화살표의 이유를 적는다. "B는 A의 함수 계약이 필요하다"처럼 문장으로 쓴다. 순서표에 먼저 적혔다는 이유만으로 선을 추가하지 않는다.
  3. 10~15분 · 시작 조건을 표로 만든다. 필요한 결과가 존재하는지, 인수 조건을 만족하는지, 실행 도구가 필요한지를 적는다. 작업 범위가 달라졌다면 관계도 함께 고친다.
  4. 15~20분 · 반례를 확인한다. 위 판정표에서 A·B만 준비한 경우와 C의 비교 검사가 빠진 경우를 골라, 왜 D를 시작할 수 없는지 각각 한 문장으로 기록한다. 가능한 순서 두 개와 시작 조건을 어기는 순서 하나를 적는다.
  5. 20~25분 · 에이전트의 검토와 대조한다. 아래 요청문을 보내고, 누락되거나 불필요한 선이 있다는 지적을 자신의 표와 대조한다. 수정한 내용과 이유를 기록하고 실행하지 않은 코드는 미실행으로 남긴다.
기대 산출물 — 시작 조건표 1개 + 이유가 붙은 관계도 1개 + 가능한 순서 2개·잘못된 순서 1개 + 반례 판단 근거 2줄.

메모만 작성한 경우 결과는 의존성 설계와 조건 검토다. 함수 구현이나 테스트 실행까지 완료한 것으로 표시하지 않는다.

바로 쓰는 검토 요청문

string BuildTransferSummary(long sent, long total)
total > 0, 0 <= sent <= total이면 정상 입력.
진행 중은 "진행 중 N%" (백분율 소수점 버림).
sent == total이면 "전송 완료 100%".
정상 범위 밖 입력은 "전송 정보 오류".
예: (1,3)→"진행 중 33%", (100,100)→"전송 완료 100%",
(0,0), (101,100)→"전송 정보 오류".

작업 범위
A: 함수 계약과 예상값 표를 고정.
B: A를 기준으로 구현 소스를 작성·검토. 실행 결과는 아직 요구하지 않음.
C: A를 기준으로 검사 소스를 작성·검토. 실제 실행은 D에서 함.
D: B와 C를 연결해 전체 검사를 실제 실행하고 결과 기록.

내 관계 초안
A→B, A→C, B→D, C→D.
각 화살표는 후속 작업이 요구하는 산출물을 뜻함.

검토 결과
1. 각 작업의 선행 결과·시작 조건·산출물을 표로 작성.
2. 누락되거나 불필요한 의존 관계가 있으면 구체적 이유 설명.
3. 가능한 실행 순서 두 개와 잘못된 순서 하나, 그 이유 제시.
4. A·B만 준비됐을 때 D를 시작할 수 없는 이유 설명.
5. C 파일이 있어도 비교 검사가 없을 때 조건 충족 여부 설명.

실제 저장소를 읽지 않았다면 파일명·구현 상태를 추정하지 마.
같은 파일 수정 등 충돌 가능성은 의존 관계와 별도로 표시해 줘.

결과 확인 체크리스트

  • 모든 화살표에 전달할 산출물과 필요한 이유가 있다. "목록의 앞 항목이라서"만으로 연결한 선은 제거하거나 이유를 보완했다.
  • C가 검사 소스 작성까지만인지 실제 실행까지인지 명시했다. 범위에 맞춰 B→C의 필요성을 판단했다.
  • D가 B와 C 모두를 요구한다고 적었다. B만 준비된 상황에서 D를 시작할 수 없다는 판단 근거를 남겼다.
  • 파일 존재와 인수 조건 충족을 구분했다. 비교 검사가 빠진 C는 준비 완료로 인정하지 않았다.
  • 가능한 순서 두 개와 잘못된 순서 하나를 각 작업의 시작 조건에 대조했다. 같은 결과를 기다리는 순환 관계가 생겼다면 범위를 다시 살폈다.
  • 계획 검토의 근거와 코드 실행의 증거를 구분했다. 실제 실행을 했다면 최종 코드·명령·출력을 남기고, 하지 않았다면 미실행으로 기록했다.

흔한 실수와 다음 회

'검사 코드 작성'과 '검사 실행'을 한 가지로 생각하기

검사 작성에는 계약만 필요할 수 있지만, 실제 실행에는 구현도 필요하다. 두 범위를 섞으면 실행 재료가 없는데 시작하거나, 작성 가능한 검사를 불필요하게 기다리게 된다. 작업 카드에 어디까지 마쳐야 그 산출물을 넘길 수 있는지 적어 둔다.

근거

A~D의 분해·인수 조건·표·조건 판정은 이 글의 교육용 설계다. 실제 코드나 실행 결과를 재현한 것이 아니다.
