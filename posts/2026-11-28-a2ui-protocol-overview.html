오픈 프로토콜
A2UI(Agent-to-UI)는 AI가 텍스트 대신 "화면 설명서"를 보내고, 앱이 그것을 자기 네이티브 컴포넌트로 그리는 오픈 프로토콜이다. AI는 화면의 조합만 결정하고, 어떤 부품을 쓸 수 있는지와 그 부품이 어떻게 보이는지는 개발자가 정한다. 1.0의 핵심 변화는 양방향 함수 호출, Express 추론 포맷, 서버 측 데이터 바인딩이다.
작성 기준 — 2026-11-28 시점. 유튜브 채널 '개발동생'의 A2UI 소개 영상 요약 자료를 구글 공식 블로그, Android 개발자 문서, 개발자 실측 글과 대조해 정리했다. 영상 자료와 공식 자료가 다른 부분은 본문에 따로 표시했다.

A2UI란 무엇인가

LLM의 추론 성능은 빠르게 좋아졌지만 결과를 전달하는 방식은 여전히 텍스트와 마크다운이다. 예약 하나를 바꾸려 해도 "몇 시가 좋으세요?" → "7시 반" → "그 시간은 자리가 없습니다" 같은 왕복이 여러 번 생긴다. A2UI는 이 왕복을 한 번의 인터랙티브 화면으로 대체한다. 시간 슬롯 버튼, 픽업 체크박스, 확정 버튼이 담긴 카드 하나를 띄우는 식이다.

동작 흐름

  1. 생성 — 에이전트(Gemini, Claude 등 어떤 LLM이든)가 UI 구성을 기술한 메시지를 만든다.
  2. 전송 — A2A, AG-UI, MCP, WebSocket, REST 등으로 클라이언트에 보낸다.
  3. 해석 — 클라이언트의 A2UI 렌더러가 메시지를 파싱하고 검증한다.
  4. 렌더링 — 추상 컴포넌트(예: TextField)를 앱 코드에 있는 실제 구현으로 매핑해 그린다.

핵심 개념: 카탈로그

클라이언트 앱은 미리 승인한 컴포넌트 목록, 즉 카탈로그를 가진다. 에이전트는 이 목록에 있는 부품만 요청할 수 있다. 카탈로그는 부품 이름, 속성 스키마, 사용 가능한 함수를 정의하는 에이전트와 앱 사이의 계약이다. 기본 카탈로그에는 18개 표준 컴포넌트가 들어 있다.

UI 생성 방식 3단계에서의 위치

방식내용장점한계
1. 고정 위젯미리 만든 카드를 고르고 값만 채움안전하고 디자인이 일관됨위젯이 없는 상황에는 대응 불가
2. 카탈로그 조합 (A2UI)승인된 부품을 런타임에 조립유연성과 통제력의 균형카탈로그 범위 밖은 표현 불가
3. HTML/코드 생성모델이 화면 코드를 통째로 작성표현 자유도 최대샌드박스 격리, 디자인 파편화, 코드 주입 위험

구글이 내세운 원칙은 "Accept freely, emit verifiably"다. 입력은 자유롭게 받되, 결제나 예약처럼 실제 효과가 있는 화면은 검증 가능한 부품 조합으로만 내보낸다는 뜻이다.

1.0에서 새로 생긴 것

기능내용
양방향 함수 호출렌더러가 에이전트 함수를 불러 좌석·예약 가능 시간 같은 정보를 실시간 조회할 수 있다. 반대로 에이전트도 렌더러 함수를 부를 수 있다. 호출받은 쪽은 결과나 에러를 돌려준다.
호출 권한 제어어느 쪽이 어떤 함수를 부를 수 있는지 카탈로그 권한으로 제한한다. 실제 조회·예약 로직은 개발자가 백엔드에 연결해야 한다.
카탈로그 혼합한 화면에서 여러 카탈로그의 부품을 섞어 쓸 수 있다. 모두 같은 A2UI 스펙 버전이어야 한다.
서버 측 바인딩데이터와 하위 컴포넌트를 서버에서 바인딩해 민감한 값이 모델로 넘어가지 않게 한다.
Express 포맷모델이 장황한 JSON 대신 축약 문법으로 UI를 쓰고, SDK가 이를 결정적으로 JSON으로 컴파일·검증한다. 1.0 SDK의 기본값이다.
A2UI Macros (Python)컴포넌트 확장과 데이터 바인딩을 서버 코드로 처리한다. 모델은 호출 한 줄만 쓴다.
메시지 통합0.9에서는 화면 생성·컴포넌트·데이터를 세 메시지로 보냈다. 1.0에서는 createSurface 하나에 components와 dataModel을 함께 담을 수 있다.
접근성컴포넌트 이름·설명 외에 화면 갱신 알림을 추가해 스크린리더가 변화를 따라가게 했다.

앱 개발에 도움이 되는 점

1. 설계도 하나로 여러 플랫폼 대응

에이전트는 플랫폼과 무관한 설계도 하나만 만든다. 웹(React, Angular, Lit), Flutter(모바일·웹·데스크톱), iOS(SwiftUI), Android(Jetpack Compose) 렌더러가 각자 네이티브 UI로 그린다. 서버의 에이전트 로직을 플랫폼마다 따로 만들 필요가 없다.

2. 보안 모델이 단순하다

A2UI 메시지는 실행 코드가 아니라 선언형 데이터다. 앱은 AI가 만든 HTML이나 JavaScript를 실행하지 않는다. WebView에 생성 코드를 띄우는 방식보다 보안 검토와 스토어 심사 측면에서 설명하기 쉬운 구조다.

3. 디자인 시스템이 유지된다

에이전트는 등록된 부품만 배치할 수 있으므로 브랜드 디자인 시스템을 벗어나지 않는다. 같은 JSON 설계도라도 클라이언트에서 카탈로그 구현(예: CopilotKit 스타일에서 shadcn 스타일로)을 바꾸면 모델 재호출 없이 다른 스타일로 그려진다.

4. 기존 에이전트 스택에 바로 붙는다

MCP, AG-UI, A2A, WebSocket, REST 위에서 동작하고, 웹·Flutter 렌더러는 MCP Apps 안에서도 동작한다. MCP 서버로 기기 기능을 노출하는 앱이라면 도구 결과를 텍스트가 아니라 승인 카드나 파일 선택 UI로 돌려줄 수 있다.

5. 클라이언트 코드가 줄어든다

한 개발자의 실측 사례에서 0.9에서 1.0으로 옮기며 브라우저 쪽 page.tsx가 309줄에서 150줄로 줄었다. 직접 짜던 파서와 정규화 코드가 SDK로 넘어간 덕분이다.

앱 개발에서 바뀌는 것

기존A2UI 이후
기획 단계에서 화면을 전부 확정부품(카탈로그)만 확정하고 조합은 런타임에 AI가 결정
기능마다 화면을 개발범용 컴포넌트 + 스키마 + 렌더러 매핑 개발이 중심
챗봇 응답은 텍스트챗봇 응답이 폼, 승인 카드, 차트
사람이 직접 조작하는 화면에이전트 작업을 감독하고 승인하는 화면

마지막 항목이 가장 큰 변화다. 에이전트 여러 개가 병렬로 일해도 결과를 확인하고 승인하는 사람은 한 명이고, 사람은 직렬로 판단한다. 긴 텍스트 보고서를 읽는 대신 선택지 카드 하나로 결정하게 하면 이 병목이 줄어든다.

  • Atlassian Jira — 에이전트가 작업 항목을 처리하다 판단이 필요하면 후속 질문을 인터랙티브 카드로 띄운다.
  • Gemini Notebook — 슬라이드를 바로 만들지 않고, 자료를 분석해 추천 주제와 형식을 선택지 카드로 먼저 제시한다.
  • Alation — 지표 카드와 차트를 Claude와 자사 앱 양쪽에서 같은 설계도로 렌더링한다.
  • ByteDance — 2026년 6월 Lynx용 A2UI 렌더러를 공개했다.

개발자의 역할은 "화면을 만드는 사람"에서 "AI가 쓸 부품과 그 계약(스키마·권한)을 설계하는 사람"으로 옮겨간다.

사용법

1단계: 설치 없이 체험

  • A2UI Composer — 비주얼 에디터로 A2UI JSON을 만들어 프롬프트에 붙여 넣어 볼 수 있다.
  • CopilotKit의 A2UI Playground — 브라우저에서 바로 생성·렌더링을 시험한다.
  • Restaurant Finder 퀵스타트 — Gemini 기반 ADK 에이전트와 Lit 렌더러로 전체 스택을 로컬에서 띄운다. 약 5분.

2단계: 에이전트 측 (SDK: Python, TypeScript, Dart)

카탈로그를 SDK에 로드하면 SDK가 모델용 설명(시스템 프롬프트 섹션)을 자동으로 만들고, 모델 출력이 카탈로그 규격에 맞는지 검증한다. 1.0의 기본 출력은 <a2ui> 태그 안의 Python과 비슷한 Express 문법이다.

Express 출력 예 (컴포넌트 직접 기술)
surface("main")
root__text_1 = Text("### 100.00 USD = 89.87 EUR")
root = Card(root__column_1)
Express 출력 예 (서버 측 매크로 호출)
<a2ui>
surface("conversion")
root = RateCard("USD", "EUR", 100)
</a2ui>

두 번째 예에서 모델은 RateCard 호출만 쓰고, 실제 환율 값은 서버의 @macro가 조회해 채운다. 모델이 숫자를 옮겨 적지 않으므로 토큰도 줄고 값이 틀릴 일도 없다. 생성된 UI는 채팅 텍스트가 아니라 도구 결과로 클라이언트에 전달된다.

위 코드는 dev.to의 0.9 → 1.0 비교 글에 실린 예시를 옮긴 것이다. 직접 실행해 보지는 않았다.

3단계: 클라이언트 측 (Android 예시)

Jetpack Compose 렌더러는 Jetpack 아티팩트로 배포된다. 버전은 Jetpack 릴리스 페이지에서 확인한다.

build.gradle.kts
dependencies {
    implementation("androidx.a2ui.compose:compose-runtime:<version>")
    implementation("androidx.a2ui.compose:compose-ui:<version>")
    implementation("androidx.a2ui:a2ui-model:<version>")
    implementation("androidx.a2ui:a2ui-engine:<version>")
    // Material 3 기반 기본 카탈로그
    implementation("androidx.compose.material3:material3-a2ui:<version>")

    testImplementation("androidx.a2ui.compose:compose-ui-testing:<version>")
}
아티팩트역할
compose-runtimeSnapshot 상태 기반의 세밀한 리컴포지션
compose-ui카탈로그 컴포넌트 정의 API (JSON 스키마 → Compose UI 매핑)
a2ui-model스키마 검증, 프로토콜 버전별 파싱
a2ui-engine메시지 처리
material3-a2uiMaterial 3 기본 카탈로그, 점진적 렌더링 지원
compose-ui-testingA2UI 화면 테스트 API

커스텀 카탈로그는 A2uiComponent, A2uiCatalog 인터페이스로 구현한다. 앱이 지원하는 카탈로그 버전은 에이전트와의 capability negotiation 단계에서 전달된다. 웹은 @a2ui/react 같은 렌더러 패키지로 도구 결과의 메시지를 받아 렌더링한다.

4단계: 커스텀 카탈로그 구축

  1. 부품 스키마 정의 — 사용할 컴포넌트 이름과 속성(이름, 타입, 필수 여부, 제약)을 선언한다.
  2. 에이전트 SDK에 등록 — SDK가 모델용 설명을 자동으로 만들고 출력 설계도를 검증한다.
  3. 클라이언트 렌더러 등록 — 같은 컴포넌트 이름으로 실제 UI 구현을 매핑한다.

중요한 점과 함정

플랫폼마다 지원 버전이 다르다 — Jetpack Compose 렌더러는 아직 A2UI 0.9.1 스펙을 지원하고, 1.0 지원은 "곧"이라고만 발표됐다. Gemini도 0.9.1을 렌더링하며 Gemini Enterprise는 1.0으로 업그레이드 중이다. Android에 지금 적용한다면 0.9.1 기준으로 개발하고 1.0 마이그레이션을 계획해야 한다.
Windows 네이티브 렌더러는 없다 — 데스크톱은 Flutter와 웹 렌더러뿐이다. WinUI나 WPF 앱이라면 WebView2에 웹 렌더러를 올리거나 렌더러를 직접 구현해야 한다.

"Express 61% 절감"은 공식 수치가 아니다

영상 요약 자료에는 Express 모드가 토큰을 61% 줄인다고 나오지만, 구글 공식 블로그의 표현은 "Direct JSON 대비 최대 3배 적은 토큰, 지연 시간 최대 3배 감소"다. 실제 절감 폭은 화면 구성에 따라 크게 다르다.

토큰이 줄어도 지연은 직접 재야 한다

프로젝트에 저장된 실행 기록을 분석한 글에서는 지연 중앙값이 Express 약 9.3초, Direct JSON 약 5.5초로 Express가 더 느렸다. 영상의 Claude Sonnet 실측도 텍스트 응답 6.9초(635 토큰)에 비해 A2UI 응답이 11.6초(1,904 토큰)였다. 점진적 스트리밍 렌더링(뼈대 3초, 첫 요소 5초)으로 체감 대기는 줄일 수 있지만, 자기 모델과 화면으로 직접 측정해야 한다.

메시지 이름이 버전마다 다르다

beginRendering, surfaceUpdate, dataModelUpdate는 0.8 시절 이름이고, 0.9부터는 createSurface, updateComponents, updateDataModel, deleteSurface를 쓴다. 0.9에서 1.0으로 넘어갈 때도 breaking change가 있다.

  • theme 제거
  • h1~h5 제거 (제목은 Markdown으로)
  • path / call → @path / @call
  • 버전 문자열 "1.0", 일부 컴포넌트 속성 변경

공식 저장소의 evolution guide를 보고 마이그레이션한다.

카탈로그가 모든 보안을 해결하지는 않는다

카탈로그는 "무엇을 그릴지"를 막아 주지만 "그 안에 무엇을 담을지"까지 보장하지는 않는다. 영상에서 짚은 위험은 두 가지다.

  • 이미지 URL을 통한 데이터 유출 — 모델이 이미지 주소의 쿼리 파라미터에 세션 토큰 같은 민감 정보를 실어 외부로 요청을 보낼 수 있다.
  • 숨겨진 폼 — 사용자 눈에 띄지 않는 입력 필드로 의도하지 않은 승인을 유도할 수 있다.

렌더러 바깥에 이미지·링크 도메인 화이트리스트와 값 새니타이징을 두고, 결제·전송·삭제처럼 되돌릴 수 없는 동작은 사용자 확인 단계를 거치게 해야 한다.

확인되지 않은 수치

영상 요약 자료의 GitHub 스타 18,000개 이상, 웹 패키지 주간 다운로드 140만 회는 공식 출처에서 확인하지 못했다.
