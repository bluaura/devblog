Jev는 텍스트를 생성하지 않는 "결정 모델(System One)"이다. 비정형 입력을 받아 미리 정의한 선택지·척도·예/아니오 중 하나를 확률과 함께 돌려준다. 생성과 추론은 LLM에, 그 사이사이의 빠른 판단은 Jev에 맡기는 구조가 핵심이다. 이 글은 공개 2주 시점의 자료를 바탕으로 LLM과의 차이, 장단점, awesome-jev 유즈케이스, PC-모바일 연동 앱에 적용할 수 있는 기능 아이디어를 정리한다.

Jev란 무엇인가

  • 개발사: TypeSafe AI(샌프란시스코, 2024년 설립). 시드 4,000만 달러, 기업가치 2억 달러.
  • 공개일: 2026년 9월 15일
  • 정의: "unstructured state in, typed probabilistic decisions out". 비정형 상태를 넣으면 타입이 정해진 확률적 결정이 나온다.
  • 학습: 트랜스포머 기반이며, 합성 데이터와 RLCD(Reinforcement Learning for Calibrated Decisions)로 학습했다고 밝혔다. 가중치와 상세 구조는 비공개이고 API로만 제공된다.
  • 동작 방식: 토큰을 하나씩 생성하는 autoregressive 방식이 아니라, 한 번의 패스로 결정을 출력하는 non-autoregressive 방식이다.

일반 LLM과의 차이

구분일반 LLMJev
출력자유 텍스트(토큰 순차 생성)타입 값 + 확률(단일 패스)
질문 형식자유 프롬프트Choice(최대 255개 보기) / Score(2~10단계) / Noul(0~1 확률)
응답 속도수 초70~500ms, 결정 루프를 초당 약 10회
비용입력·출력 모두 과금입력만 과금($0.042/1M), 출력 무료
신뢰도 신호드러나지 않고 과신하기 쉬움보정된 probabilities와 confidence 반환
질문 여러 개질문이 늘면 시간도 증가한 번의 호출 안에서 병렬로 평가, 지연 증가가 거의 없음
스키마 오류발생 가능구조적으로 0%(정의 밖의 값은 반환 불가)

TypeSafe는 "40~200배 빠르고 40~400배 싸다"(최대 193.6배, 444.6배)고 주장한다. 다만 모두 자사 벤치마크 수치이고 독립 검증은 아직 부족하다.

API 구조와 제약

엔드포인트는 POST https://api.typesafe.ai/v1/systemone 이다. 요청은 state(문자열·객체·배열)와 이름 붙인 questions 로 구성된다. 아래 코드는 공개 가이드를 바탕으로 작성한 미검증 예시다(typesafe-sdk, 2026년 9월 기준).

jev_example.py (미검증)
from typesafe import TypeSafe, Choice, Score, Noul  # pip install typesafe-sdk

client = TypeSafe()  # TYPESAFE_API_KEY 환경변수 사용

res = client.evaluate(
    model="jev-1.13.0",  # jev-latest 대신 버전 고정 권장
    state={"message": "PC에 있는 계약서 폴더 전체를 폰으로 보내고 원본은 지워줘"},
    questions={
        "intent": Choice(
            instructions="사용자가 원하는 기기 동작",
            criteria={
                "file_transfer": "PC와 폰 사이 파일 송수신",
                "clipboard": "클립보드 동기화",
                "media_import": "폰 사진/영상 가져오기",
                "other": "그 외",
            },
        ),
        "risk": Score(
            instructions="실행 시 데이터 손실·유출 위험도",
            criteria=["없음", "낮음", "중간", "높음"],
        ),
        "destructive": Noul(instructions="요청에 삭제나 덮어쓰기가 포함되는가"),
    },
)

a = res.answers
print(a["intent"].choice, a["intent"].confidence)
print(a["risk"].score, a["destructive"].noul)

장점과 단점

장점

  • 잘못된 형식의 출력이 없다: 답의 범위를 미리 정의하므로 스키마 밖의 값은 나오지 않는다.
  • 도입이 쉽다: 학습 데이터나 파인튜닝 없이 프롬프트만으로 분류기를 만들 수 있다.
  • confidence를 제어 흐름에 쓸 수 있다: 자동 실행할지, 사람에게 넘길지를 코드에서 분기한다.
  • 지연과 비용이 낮다: 실시간 루프나 대량 처리에 넣어도 경제성이 맞는다.

단점

  • 텍스트 생성, 코드 작성, 긴 추론이 불가능하다. 파라미터 추출(예: 문장에서 날짜 뽑기)도 할 수 없다.
  • 숫자, 날짜, 개수 세기, 적대적 입력에 약하다. 공식 가이드에서도 인정하는 부분이다.
  • 판단 근거를 설명하지 않는다.
  • 같은 입력에 대해 결과가 항상 같다는 보장이 없다.
  • "틀린 값"은 나오지 않지만 "그럴듯하게 틀린 선택지"를 높은 확신으로 고를 수는 있다.
  • API 전용이다. 온디바이스와 오프라인 실행은 불가능하다.
  • 이미지와 영상을 입력으로 받지 못한다. 화면 판단은 접근성 트리 같은 텍스트로 변환해서 넘겨야 한다.
공개 초기라 가격과 성능 수치는 출처마다 조금씩 다르다(예: 위키백과는 공개 가격이 없다고 서술). 도입 전에 자체 데이터로 정확도와 보정 수준을 먼저 검증해야 한다.

awesome-jev로 본 유즈케이스

여러 awesome-jev 저장소가 400~900여 개 오픈소스 프로젝트를 모아 두었다. 에이전트 툴링과 벤치마크 카테고리가 가장 크다.

영역예시
에이전트 감독툴 호출 전 위험도 판정과 차단, 스킬 선택, 조기 종료를 막는 stop hook
모델 라우팅요청 난이도에 따라 경량, 고성능, 추론 모델 중 하나로 배정
브라우저·컴퓨터 제어페이지 상태를 보고 다음 조작과 대상 요소를 선택 (Jev Ultrafast)
코드 리뷰PR·diff 위험도, 마이그레이션 안전성 판정
RAG 품질문서 조각별 관련성, 모순, 인젝션 위험 점수로 필터링
컨텍스트 최적화코딩 에이전트의 컨텍스트 압축 (fast-jev-compaction)
도메인 분류CS 티켓 분류, 사기 탐지, 모더레이션, 리드 스코어링
실시간 제어게임 NPC, 센서 판단, 드론 시뮬레이션(시뮬레이터 한정)
모바일 QA접근성 트리 기반 UI 자동화 (jev-android, Callstack agent-device: 테스트 1회 14초, $0.0023)

LLM과 시너지를 내는 패턴

원칙은 하나다. 생성과 추론은 LLM이 하고, 그 사이의 판단은 Jev가 한다.

  1. Confidence 게이팅: Jev는 "무엇인지"만 답하고, "실행할지"는 앱 코드의 임계값이 정한다. 되돌릴 수 있는 작업은 임계값을 낮게, 위험한 작업은 높게 두고, 애매하면 사람에게 넘긴다.
  2. 투기적 팬아웃: 필요할지도 모르는 질문까지 한 번의 호출에 묶는다. 출력이 무료이고 병렬로 처리되므로 비용과 지연이 거의 늘지 않는다.
  3. 원자 점수 조합: 점수 하나 대신 차원별 점수를 받고, 가중치는 앱에서 직접 조합한다.
  4. LLM 앞뒤에 배치: 앞단에서는 의도 분류, 모델 라우팅, RAG 필터링을, 뒷단에서는 출력 검증을 맡긴다.
  5. Retrieve, then judge: 검색과 필터링은 코드로 먼저 하고, 판단에 필요한 필드만 보낸다. 숫자와 날짜 계산도 코드에서 끝낸다.

PC-모바일 연동 앱에 적용한다면

Wi-Fi, BT, BLE 기반의 파일 전송, 미러링, 화면 확장 앱을 전제로 적합도순으로 정리했다.

기능Jev 사용 방식적합도
에이전트 툴 호출 위험도 판정툴 호출 내용을 Score(risk)로 판정. low는 자동 허용, mid는 폰 승인, high는 생체인증최상
알림 미러링 우선순위알림 텍스트를 Score(urgency)와 Choice(category)로 판정해 긴급한 것만 PC에 표시상
자연어 명령 라우팅Choice(intent)로 의도를 고르고, 파라미터 추출은 LLM이나 규칙이 담당(2단 구조)상
상황 인식 워크스페이스실행 앱, 일정, 연결된 디스플레이 상태를 보고 Choice(scene)로 레이아웃 추천중상
클립보드·파일 민감정보 감지Noul로 판정. 로컬 정규식이 1차, Jev에는 메타데이터만 전송중
연결 앱 UI 회귀 테스트접근성 트리 기반 QA 자동화중
보안 원칙: 에이전트나 사용자가 만든 입력은 적대적일 수 있다. Jev 판정은 위험도를 올리는 용도로만 쓰고, "셸 명령은 항상 high" 같은 기본 정책은 코드에 고정한다. API 실패나 오프라인일 때는 fail-closed로 처리한다.

맞지 않는 영역

  • 미러링·화면 확장의 프레임 단위 제어: 70~500ms 지연으로는 맞출 수 없다.
  • Wi-Fi/BT/BLE 채널 선택, 재연결 판단: RSSI나 대역폭 같은 숫자 비교 문제라 결정론적 코드가 더 정확하다.
  • 오프라인에서도 동작해야 하는 핵심 경로: API 전용이라 네트워크가 끊기면 쓸 수 없다.

구현 체크리스트

  • API 키는 클라이언트 앱에 넣지 않는다. PC 측 에이전트 프로세스나 릴레이 서버에서 호출한다.
  • 모델 버전을 고정해 임계값이 모델 업데이트로 흔들리지 않게 한다.
  • 여러 질문을 한 번의 호출로 묶는다.
  • Kotlin/Swift 앱에서는 커뮤니티 SDK를 쓰거나 REST를 직접 호출한다(비공식이므로 검토 필요).

정리

질문답
Jev가 LLM을 대체하나아니다. 텍스트 생성이 불가능하고, LLM 파이프라인 속 판단 단계를 대체하는 역할이다.
가장 잘 맞는 일답의 범위가 유한하고, 결과가 코드 분기로 이어지며, 자주 호출되는 판단
가장 큰 리스크숫자·날짜·적대적 입력에 약함, 설명 불가, 클라우드 의존, 자사 벤치마크 위주의 검증
연동 앱에서 첫 적용 후보에이전트 툴 호출 위험도 판정과 알림 우선순위 필터
