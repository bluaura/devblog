요구사항

  • 대상: 북스캔 PDF(이미지 전용), 한국어 위주 + 영어 혼용 단행본, 코드·수식·표가 있는 기술서 포함. 손글씨 없음.
  • 분량: 50~300권, 약 2만~10만 페이지.
  • 우선순위: 정확도 최우선. 처리시간은 며칠 걸려도 무방.
  • 결과물: 검색가능 PDF(투명 텍스트 레이어) + 페이지별 텍스트/마크다운 파일.
  • 환경: MacBook Pro M5 Pro. 로컬(NPU 포함)과 클라우드 모두 검토. 개인용, 비상용.

Apple Vision — 로컬 한글 OCR의 기준

macOS 13부터 VNRecognizeTextRequest가 한국어를 지원했고, macOS 26에서 추가된 RecognizeDocumentsRequest는 문단·줄·단어·표·리스트·읽기 순서를 계층 구조로 돌려준다. 완전 온디바이스이며 26개 언어를 지원한다. 국내 사용자 보고 기준으로 로컬 엔진 중 한글 인쇄체 정확도가 가장 높다. EasyOCR 대비 약 10배 빠르고, M3 Max에서 이미지당 0.13~0.2초가 측정되었다.

알려진 약점은 한글과 한자가 섞인 페이지다. 우선 언어를 ko-KR로 두면 한자가 빠지고, 반대로 두면 한글이 흔들린다. 한자 비중이 높은 페이지는 zh-Hant 우선으로 한 번 더 돌려 병합하는 후처리가 필요하다.

Python에서 바로 쓰는 방법

ocrmypdf-appleocr 플러그인(v0.4.0, 2026-07)을 설치하면 OCRmyPDF가 Tesseract 대신 Vision을 호출한다. accurate/livetext 모드에서 한국어를 지원하고, CJK용 sandwich 렌더러가 기본이다.

terminal
pip install ocrmypdf ocrmypdf-appleocr
ocrmypdf -l kor --sidecar out.txt --output-type pdfa in.pdf out.pdf

--sidecar로 텍스트 파일이 함께 생성되므로 "검색가능 PDF + 텍스트" 요구사항을 한 줄로 충족한다. 좌표·confidence까지 필요하면 ocrmac(pyobjc 래퍼)을 쓴다.

vision_ocr.py
from ocrmac import ocrmac

# framework="livetext" 가 최신 API, 세로쓰기 CJK도 처리
ann = ocrmac.OCR("page_0001.png",
                 language_preference=["ko-KR", "en-US"],
                 framework="livetext").recognize()
for text, confidence, bbox in ann:
    print(confidence, bbox, text)
참고 — RecognizeDocumentsRequest(표·읽기순서 반환)는 아직 Python 래퍼가 없어 Swift에서 직접 호출해야 한다. 앱을 제대로 만든다면 Swift CLI 또는 macOS 앱이 가장 자연스럽다.

1순위는 GLM-OCR이다. 가볍고, 한국어를 공식 지원하며, 문서 벤치마크 최상위다. 코드·수식 페이지에서 더 유연한 출력이 필요하면 Qwen3-VL-8B를 2순위로 둔다. 10만 페이지 전체를 VLM으로 돌리면 GLM-OCR 기준 3.5~6일 연속 실행이 필요하므로, 기술서 페이지만 선별 처리하는 편이 현실적이다.

멀티모달 LLM(Gemini·Claude·GPT) OCR

페이지당 입력 토큰은 Gemini PDF 입력 258토큰(다운샘플링되어 작은 한글·코드에 불리, 기술서는 이미지 입력 약 1,500토큰 권장), Claude 약 1,568(표준)/4,784(고해상도), GPT 약 1,000~1,600이다. 출력은 밀도 높은 한국어+코드 페이지 기준 약 2,000토큰. 배치 API는 50% 할인된다.

실제 비용은 텍스트 밀도에 따라 ±40% 변동한다.

한국어 근거로는 KO-VLM-Benchmark(실제 한국어 문서)에서 Gemini 2.5 Pro 91.8% vs Qwen3-VL-8B 56.3%로 프론티어 폐쇄 모델이 오픈 VLM을 크게 앞선다. 반면 OmniDocBench(중·영)에서는 GLM-OCR 94.6 > Gemini 3 Pro 90.3 > GPT-4o 75.0으로 전용 OCR 모델이 LLM을 앞선다.

주의 — LLM OCR의 핵심 리스크는 환각이다. 코드·수식·숫자를 그럴듯하게 고치거나 줄을 건너뛰어도 형식 검사로는 잡히지 않는다. 고전 OCR(Vision) 결과와 문자열 diff로 검증하는 QA 단계 없이 단독 사용하면 안 된다. 신규 계정의 동기 API는 레이트리밋에 걸리므로 배치 API를 쓴다.

탈락한 후보와 이유

후보탈락 이유
Tesseract 5 (kor)진지한 후보 중 한글 정확도 최하. 코드·수식·레이아웃 미지원. 검색가능 PDF 파이프라인(OCRmyPDF)은 훌륭하나 엔진만 Vision으로 교체하는 편이 낫다.
EasyOCR국내 비교에서 한글 "매우 떨어짐" 평가, 2024-09 이후 릴리즈 없음. Vision 대비 6배 느림.
PaddleOCR PP-OCRv5 (고전 파이프라인)한국어 모델은 mobile만 존재(라인 정확도 88.0%), macOS는 CPU 전용, 설치 마찰 큼. Vision 대비 우위 근거 없음. 보조 후보로만 유지.
Naver CLOVA OCR정확도는 최상이지만 ₩25/페이지로 10만 페이지 ₩250만. 1 TPS 권장 제한.
AWS Textract한국어 미지원 확인.
olmOCR학습 데이터 대부분 영어. 비영어는 "기본 수준".

검색가능 PDF 텍스트 레이어 만드는 4가지 방법

  1. OCRmyPDF + Apple 플러그인 — 가장 간단. --sidecar로 텍스트 파일도 함께 생성.
  2. mac-ocr(npm) — Vision 결과를 CoreText로 단어 단위 투명 텍스트 삽입. -l ko-KR -l en-US 다중 언어 지원.
  3. PyMuPDF 직접 구현 — 좌표 있는 엔진(ocrmac, PaddleOCR, Surya) 결과를 투명 텍스트로 삽입. PyMuPDF 내장 CJK 폰트로 한글 검색 가능.
  4. VLM 마크다운은 사이드카로 — 좌표가 없으므로 .md로 따로 저장하고 SQLite FTS5 인덱스에 Vision 텍스트와 함께 색인.
add_text_layer.py
import fitz  # PyMuPDF

doc = fitz.open("scan.pdf")
page = doc[0]
# lines: [(text, x0, y0, x1, y1), ...] — Vision/ocrmac 결과를 페이지 좌표로 변환한 것
for text, x0, y0, x1, y1 in lines:
    fontsize = max(4, (y1 - y0) * 0.8)
    page.insert_text((x0, y1), text, fontsize=fontsize,
                     fontname="korea",   # PyMuPDF 내장 CJK 폰트
                     render_mode=3)      # 3 = 투명(보이지 않지만 검색·선택 가능)
doc.save("scan_searchable.pdf")

위 코드는 개념 확인용 의사코드에 가깝다. 실제로는 bbox 정규화 좌표를 페이지 픽셀 좌표로 변환하고, 세로쓰기·회전 페이지를 별도 처리해야 한다.

권장 아키텍처

  1. Phase 1 (전량, 로컬·무료) — Swift CLI 또는 Python(ocrmac / ocrmypdf-appleocr)으로 전 PDF를 Apple Vision(ko-KR 우선, livetext 모드, 300dpi 렌더링) 처리. 검색가능 PDF + 페이지별 JSON(텍스트·bbox·confidence) 생성. 한자 다수 페이지는 zh-Hant 우선으로 재실행 후 병합.
  2. Phase 2 (선별, 로컬·무료) — 기술서 페이지, Phase 1에서 confidence가 낮은 페이지, 표·코드가 감지된 페이지만 GLM-OCR(Ollama) 또는 Qwen3-VL-8B(MLX)로 마크다운 생성.
  3. Phase 3 (QA) — Vision 텍스트와 VLM 텍스트의 문자열 유사도를 비교해 불일치율 높은 페이지를 목록화. 필요하면 그 소수 페이지만 Upstage Document Parse 또는 Gemini Flash 배치로 3차 판정(수백~수천 페이지면 $10 미만).
  4. 검색 — SQLite FTS5(trigram 토크나이저로 한글 부분일치) 또는 검색가능 PDF만으로 Spotlight/Finder 검색.
예산 $150~1,000이 허용된다면 — Phase 1을 Google Document AI OCR($150/10만p), Phase 2를 Upstage Document Parse로 대체하면 설치·튜닝 없이 수 시간 내 끝난다. 다만 Vision의 한글 품질이 Google과 동급 이상이라 로컬 우선이 합리적이다.
