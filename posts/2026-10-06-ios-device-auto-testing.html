작성일: 2026-10-06 (KST). 자동 검증 프로그램을 만들기 전 사전 조사 노트다. 명령 예시는 문서 기준으로 정리했으며 직접 실행해 검증하지는 않았다. 옵션은 Xcode 버전에 따라 다를 수 있다.

맥용 테스트 프로그램으로 아이폰 앱을 자동 테스트하는 것은 가능하다. xcodebuild와 devicectl이 adb 역할을 하고, UI 조작은 아이폰 안에서 도는 XCUITest 러너가 맡는다. 요소 탐색은 화면 인식이 아니라 접근성 ID 기반이 기본이며, 아이폰의 백그라운드 제약은 테스트 러너에는 적용되지 않는다.

1. 사전 준비

  1. 아이폰을 케이블로 연결하고 "이 컴퓨터를 신뢰" 승인.
  2. 설정 > 개인정보 보호 및 보안 > 개발자 모드 켜기(재부팅 필요). 안드로이드의 USB 디버깅에 해당한다.
  3. Xcode에서 Apple 계정으로 서명 팀 설정. 무료 계정도 가능하지만 앱이 7일 뒤 만료된다.
  4. 이후에는 같은 네트워크에서 무선 연결도 가능하다.

기기 관리 devicectl 기기 목록, 앱 설치·삭제·실행, 파일 복사, 프로세스 조회

3. xcodebuild

terminal
# 빌드 후 실기기에서 테스트 실행
xcodebuild test \
  -scheme MyApp \
  -destination 'platform=iOS,id=<UDID>' \
  -allowProvisioningUpdates \
  -resultBundlePath out.xcresult

# 결과를 JSON으로 추출
xcrun xcresulttool get test-results summary --path out.xcresult
  • 주요 동작: build, test, build-for-testing(빌드만), test-without-building(빌드 없이 반복 실행).
  • 기기 지정: -destination 'platform=iOS,id=<UDID>'. 사용 가능한 대상은 xcodebuild -showdestinations -scheme <스킴>으로 확인한다.
  • 서명 자동 처리: -allowProvisioningUpdates.
  • 케이스 선택: -only-testing:타깃/클래스/메서드, -skip-testing:, -testPlan.
  • 불안정 테스트 대응: -retry-tests-on-failure, -test-iterations <N>.
  • 판정: 종료 코드가 0이면 전체 통과다. 케이스별 결과와 실패 시점 스크린샷은 xcresult 번들에 들어 있다.

4. devicectl

Xcode 15에서 도입됐고 iOS 17 이상 기기를 지원한다.

terminal
xcrun devicectl list devices
xcrun devicectl device install app --device <ID> MyApp.app
xcrun devicectl device process launch --device <ID> --console <번들ID>
xcrun devicectl device copy from --device <ID> \
  --domain-type appDataContainer --domain-identifier <번들ID> \
  --source Documents/result.json --destination ./result.json
  • 기기: list devices, device info details, device info lockState, device reboot, manage pair.
  • 앱: device install app, device uninstall app, device info apps.
  • 프로세스: device process launch(--console로 앱 출력 확인, --terminate-existing으로 재시작), device info processes.
  • 파일: device copy from/to, device info files. 앱 컨테이너는 --domain-type appDataContainer --domain-identifier <번들ID>로 지정한다.
  • 자동화용 출력: 모든 명령에 --json-output <파일>을 붙이면 파싱하기 쉽다.
  • 한계: 스크린샷, UI 입력, 시스템 전체 로그 스트림이 없다. 폴더 단위 재귀 복사도 안 된다.

5. adb 대응 관계

하려는 일 Android iOS
디버깅 허용 USB 디버깅 개발자 모드 + 컴퓨터 신뢰
기기 목록 adb devices devicectl list devices
기기 정보 adb shell getprop devicectl device info details
설치 / 삭제 adb install / uninstall devicectl device install app / uninstall app
설치된 앱 목록 pm list packages devicectl device info apps
앱 실행 am start devicectl device process launch
파일 복사 adb pull / push devicectl device copy from / to
로그 adb logcat --console(앱 출력), Console 앱, pymobiledevice3 syslog live
테스트 실행 am instrument xcodebuild test
UI 트리 덤프 uiautomator dump XCUITest의 debugDescription, WDA의 /source
탭·입력 adb shell input XCUITest / WDA만 가능
스크린샷 adb shell screencap XCUITest의 screenshot(), pymobiledevice3 developer dvt screenshot
포트 포워딩 adb forward pymobiledevice3 usbmux forward, iproxy

재부팅 adb reboot devicectl device reboot
셸 adb shell 없음

안드로이드와 다른 점

  • 셸이 없다. 기기 안에서 임의 명령을 실행할 수 없다.
  • UI 조작은 테스트 러너를 거쳐야 한다. adb shell input tap 같은 직접 명령이 없다.
  • 서명이 필수다. 서명되지 않은 앱은 실기기에 설치되지 않는다.

6. 맥용 테스트 프로그램의 구조

UI 조작 명령은 아이폰 안에서 도는 테스트 러너 앱이 실행해야 하므로 "맥의 지휘 프로그램 + 아이폰의 러너" 구조가 된다.

방식 동작 적합한 경우
A. xcodebuild 지휘형 테스트를 Swift XCUITest로 작성하고, 맥 프로그램이 xcodebuild test를 호출해 xcresult를 읽는다 정해진 시나리오의 회귀 테스트. 가장 단순하고 안정적
B. 실시간 조작형 러너가 아이폰에서 HTTP 서버를 띄우고(WebDriverAgent), 맥이 포트 포워딩으로 명령을 보낸다 맥 쪽에서 단계별로 판단하며 조작해야 하는 탐색형 테스트
  • 소스 없는 앱도 XCUIApplication(bundleIdentifier:)로 대상으로 삼을 수 있다. 서명이 필요한 것은 러너 쪽이다.
  • Appium 문서에 따르면 iOS 27부터는 devicectl로 WDA를 띄우는 방식이 막혀 xcodebuild나 RemoteXPC 터널로 시작해야 한다.

7. 요소 탐색: 화면 인식이 아니라 ID 기반

XCUITest는 접근성 요소 트리를 조회하며 화면 픽셀을 분석하지 않는다.

TransferTests.swift
let app = XCUIApplication()
app.launch()

let send = app.buttons["sendButton"]   // accessibilityIdentifier로 조회
XCTAssertTrue(send.waitForExistence(timeout: 10))
send.tap()

XCTAssertTrue(app.staticTexts["transferDone"].waitForExistence(timeout: 30))
  • 앱 코드에서 accessibilityIdentifier를 달아두는 것이 가장 안정적이다. 화면에 보이지 않는 값이라 문구나 언어가 바뀌어도 깨지지 않는다.
  • 요소 종류, 표시 텍스트, 조건식으로도 찾을 수 있다.
  • waitForExistence(timeout:)로 요소가 나타날 때까지 기다린다.
  • 게임, 캔버스, 접근성 정보가 없는 커스텀 뷰는 스크린샷과 좌표 탭으로 처리해야 한다.

8. 포그라운드, 유선, 백그라운드 제약

  • 대상 앱은 포그라운드여야 조작된다. app.launch()나 app.activate()가 앱을 앞으로 가져온다.
  • 러너는 백그라운드 제약을 받지 않는다. 테스트 세션 동안 시스템 테스트 데몬의 지원을 받아 살아 있고, 대상 앱이 앞에 있는 동안 뒤에서 이벤트를 주입한다.
  • 백그라운드 전환도 테스트된다. XCUIDevice.shared.press(.home)으로 홈으로 보내고 app.state로 .runningBackground 여부를 확인한 뒤 다시 activate()할 수 있다. 설정 앱이나 시스템 권한 팝업도 번들 ID로 조작된다.
  • 유선은 최초 페어링에만 필수다. 무선도 되지만 자동 테스트에는 유선이 안정적이다.
  • 기기는 잠금 해제 상태여야 한다. 화면이 꺼지면 UI 테스트가 실패하므로 자동 잠금을 끈다.
  • 앱 내부 상태는 직접 읽을 수 없다. 러너와 대상 앱은 별도 프로세스다. 실행 인자, 로그, 컨테이너 파일로 확인한다.
  • 대상 앱이 백그라운드에서 얼마나 동작하는지는 iOS 규칙을 그대로 따른다. 실제 사용 조건과 같으므로 그 자체가 테스트 대상이다.

9. 자동 검증 설계: 조작과 판정을 분리한다

테스트를 실행하는 쪽(스크립트든 AI 에이전트든)이 "성공했다"고 보고하는 것을 판정 기준으로 쓰지 않는다. 판정은 별도 모듈이 결정적 조건으로 내린다.

구조

  1. 테스트 케이스 정의: Given/When/Then 형식. Then은 기계가 확인할 수 있는 조건으로 적는다(예: 식별자 transferDone 요소가 30초 안에 나타남).
  2. 기기 제어 계층: XCUITest 또는 WebDriverAgent를 감싸 tap, type, swipe, launch, waitFor 같은 동작으로 노출한다.
  3. 관찰: 접근성 요소 트리가 기본, 스크린샷은 보조.
  4. 판정기(오라클): 조작이 끝난 뒤 독립적으로 조건을 검사한다.
  5. 리포트: 단계별 스크린샷, 요소 트리, 로그, 영상을 남기고 JUnit XML로 출력하면 CI에 바로 붙는다.

판정 방법의 우선순위

  • 1순위, 결정적 검증: UI 요소의 존재·값, 앱 로그, 앱 컨테이너의 파일·DB, 네트워크 요청(목 서버나 프록시), 서버 상태.
  • 2순위, 스냅샷 비교: 기준 스크린샷과의 차이로 레이아웃 깨짐을 잡는다.
  • 3순위, 시각 판정: 위 방법으로 안 되는 것에만 쓴다. 조작한 주체와 분리하고 판정 근거를 함께 남긴다.

결과 구분

결과 의미
PASS / FAIL 앱이 기대대로 동작했는지 여부
BLOCKED 화면을 못 찾았거나 환경 문제로 검증까지 못 간 경우
FLAKY 재실행 시 결과가 바뀌는 경우. 실패 케이스는 2~3회 자동 재실행해 분류

BLOCKED를 FAIL과 섞으면 앱 버그와 테스트 도구의 실수를 구별할 수 없다.

안정성을 위한 설계

  • 매 케이스 초기화: 앱 재설치, 고정된 로케일·시간, 목 서버, 애니메이션 끄기로 시작 상태를 동일하게 맞춘다.
  • 기록 후 재생: 한 번 성공한 조작 경로는 스크립트로 저장해 그대로 재생하고, 재생이 깨질 때만 경로를 다시 찾는다.
  • 한도 설정: 케이스당 최대 단계 수와 시간 제한을 둔다.

기기 간 연동 기능을 테스트한다면

  • 시뮬레이터는 Bluetooth를 지원하지 않으므로 실기기가 필요하다.
  • 판정을 양쪽에서 한다. 파일 전송은 iOS 화면의 완료 표시만이 아니라 상대 기기에 도착한 파일의 해시까지 비교한다.
  • 연결 끊김, 권한 거부 같은 실패 상황은 테스트용 실행 인자나 훅으로 주입한다.
