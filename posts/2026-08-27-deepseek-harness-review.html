DeepSeek Harness(dsh)는 "Everything is a Plugin"을 내세운 오픈소스 코딩 에이전트 런타임이다. Claude Code나 Codex CLI가 완성된 에이전트에 확장 포인트를 붙인 구조라면, dsh는 에이전트 루프 자체까지 교체 가능한 마이크로커널이다. 구조적으로는 현재 나온 하네스 중 가장 잘 분해되어 있지만, 사용성과 성숙도는 아직 프리뷰 수준이다. 앱 개발자이면서 AI 보조 개발에 관심 있는 입장에서 이용자 관점과 아키텍트 관점을 나눠 정리했다.

기본 팩트

2026년 8월 13일 DeepSeek-V4-Pro(1.6T 파라미터, 토큰당 49B 활성, 1M 컨텍스트)와 함께 공개됐다. MIT 라이선스, TypeScript/Node.js 22.19 이상, pnpm 모노레포 구조다. 설치와 실행은 한 줄이다.

terminal
export DEEPSEEK_API_KEY=YOUR_API_KEY
npx @deepseek-ai/dsh web
# Web UI: http://127.0.0.1:3080

Web UI 외에 CLI와 Python SDK가 있다. 모델은 DeepSeek에 묶여 있지 않고 Anthropic, OpenAI, AWS Bedrock, Azure, Gemini, OpenAI 호환 게이트웨이, Ollama 같은 로컬 서버까지 붙는다. 특이하게 Claude Code와 Codex를 서브에이전트로 호출하는 브리지가 들어 있어, dsh를 플래너로 두고 실제 작업을 다른 에이전트에 위임하는 구성도 가능하다.

같은 날 API 가격이 인상됐다(8월 16일 적용). V4-Flash 오프피크 기준 입력 $0.22/M, 출력 $0.66/M, V4-Pro는 $0.66/M, $1.98/M이다. 이전 대비 1.5~2.3배 올랐지만 여전히 Claude 대비 크게 저렴하다.

V4-Flash-0731의 공식 벤치마크(Terminal Bench 2.1 82.7 vs Claude Opus 4.8 85.0)는 Harness의 Minimal 모드로 측정됐다. 즉 발표된 점수는 모델 단독이 아니라 모델과 하네스의 합산 결과다. 다른 런타임에서 재현하면 차이가 날 수 있다.

공개 직후 GitHub 스타가 수만 개 붙었지만, DeepSeek는 외부 PR을 받지 않는다. 기여는 커뮤니티 플러그인과 Discussion으로만 유도한다.

다른 하네스와 무엇이 다른가

첫째, 특권 코어가 없다. Claude Code, Codex CLI, Qwen Code, Kimi CLI는 완성된 에이전트 위에 MCP, hooks, plugins 같은 확장 포인트를 제공한다. dsh는 모델 어댑터, 툴 레지스트리, 세션 로그, 에이전트 루프 자체가 모두 교체 가능한 플러그인이라 코어를 패치할 필요 없이 어떤 부품이든 갈아끼울 수 있다.

둘째, 네 가지 런타임 모드가 프리셋으로 제공된다.

모드구성용도
Standard파일시스템, 쉘, 웹 검색, 플래닝, 서브에이전트 전체일반 코딩 에이전트
Code툴을 TypeScript SDK로 노출, 모델이 코드로 오케스트레이션다단계 툴콜 왕복 비용 절감
Minimalbash와 텍스트 에디터 두 개만공식 벤치마크 측정용
Creator커스텀 프리셋 개발 환경플러그인 테스트, 진단

셋째, append-only 세션 이벤트 로그가 1급 시민이다. 시스템 프롬프트, 추론, 툴 호출과 결과, 컨텍스트 주입, 서브에이전트 스케줄링까지 모델이 본 모든 것이 기록되고, resume, fork, replay, 전문 검색, 텔레메트리가 이 하나의 스트림에서 파생된다. 자율 에이전트를 디버깅하거나 재현할 때 다른 도구보다 투명하다.

넷째, 설정이 코드가 아니라 YAML 플러그인 트리이며 핫리로드된다. 소스를 건드리지 않고 설정 파일만 바꿔 모델 엔드포인트나 실행 워크플로를 교체할 수 있다.

내부 구조: Cordis 커널과 3계층 설정

커널은 Cordis라는 메타 프레임워크다. DeepSeek는 이 설계를 "A Programming Paradigm for Spatiotemporal Composability"라는 논문으로 설명한다. 핵심 개념은 다섯 가지다.

  1. Context — 공유 런타임 컨테이너. 런처가 루트 Context를 만들고 cordis.yml을 읽어 Loader 플러그인이 나머지를 마운트한다.
  2. Plugin — ctx를 인자로 받아 기능을 등록하는 함수. 툴, LLM 어댑터, 파일 접근, 에이전트 루프 전부 이 형태다.
  3. Service — ctx에 노출되는 기능. 다른 플러그인은 inject로 필요한 서비스를 선언해 의존성 주입을 받는다.
  4. Event — 타입드 이벤트 시스템. broadcast 방식과 waterfall(조건 충족 시 단락) 방식을 지원하며 declaration merging으로 이벤트 인터페이스를 확장한다.
  5. Lifecycle / Fiber — mount와 unmount 단계가 있고, 플러그인이 내려가면 그 플러그인이 등록한 서비스, 리스너, 툴이 자동으로 정리된다. 세션마다 격리된 fiber에 마운트된다.

설정은 세 층으로 쌓인다.

계층역할예
Bundle플러그인 묶음, 런타임 토대Base(LLM, 세션 저장), Headless(쉘 툴), Web-App(API 게이트웨이, WebSocket)
Profile번들 조합에 오버라이드 적용cordis.patch.yml로 엔드포인트, 경로 등 배포별 값 덮어쓰기
Agent Preset세션별 페르소나지시문, 툴 접근 범위, 서브에이전트 정책을 YAML로 정의, 디렉토리 자동 발견

프리셋은 세션 전용 fiber에 마운트되므로 한 인스턴스가 완전히 다른 툴셋과 정체성을 가진 에이전트 여러 개를 동시에 호스팅할 수 있다. 설정 파일 형태는 다음과 같다(카탈로그 문서 기준, 옵션명은 프리뷰 중 바뀔 수 있다).

cordis.yml
- dsh-agent-loop:
    maxParallelToolCalls: 2

- dsh-llm-deepseek:
    apiKeyEnv: DEEPSEEK_API_KEY
    thinking: enabled
    reasoningEffort: high
    maxTokens: 256000

- dsh-session-persistence-jsonl:
    root: ./.sessions
    packChunks: true
    compression: zstd

- dsh-sandbox-policy:
    mode: read-only
    workspaceRoot: /workspace

- dsh-compaction-basic:
    thresholdRatio: 0.8
    retainRatio: 0.16

문서에서 빠져 있는 부분도 있다. 컨텍스트 윈도 관리의 세부 전략, 서브에이전트 간 조율 방식, 알려진 실패 모드는 아직 정리되어 있지 않다.

이용자 관점에서 가장 자주 나오는 비판은 GitHub Discussion #326에 정리되어 있다. 요지는 "49개 패키지 줄 테니 에이전트를 직접 조립하라"는 접근이 그냥 코딩 어시스턴트를 쓰고 싶은 사람에게는 부담이고, VS Code나 Obsidian 생태계에서 봤듯 툴 등록 중복과 서비스 주입 순서 문제로 플러그인 충돌이 필연적이라는 것이다. 제안은 검증되고 동결된 기본 프로필을 제공하라는 것인데, 작성 시점 기준 유지보수자 답변은 없다.

아키텍트 관점에서는 반대로 이 분해도가 장점이다. 하네스 엔지니어링을 공부하거나 자체 에이전트 런타임을 설계하려는 사람에게는 Cordis의 Context, Service, Event, Lifecycle 구조와 3계층 설정이 현재 공개된 코드 중 가장 참고할 만한 레퍼런스다.
